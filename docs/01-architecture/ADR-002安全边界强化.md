# ADR-002：运行期安全边界强化（授权、取消、历史、模型、BGE、API）

> - 状态：Accepted
> - 日期：2026-09-29
> - 基线 HEAD：`5d6c1ae`
> - 首次修复终点：`92fec17`
> - 跟进修订：2026-10-01，终点 `8ebde01`（见 §2.8 与 §4）
> - 决策原则：公开契约不提供旁路；边界校验一律 fail closed；不得用"看起来安全"替代"可证明安全"。

## 1. 背景

封版后逆向复核发现 7 处**公开契约与实现不一致**或**边界缺失**：部分能力在文档里已经声明为
受限，但公开入口仍可绕过；部分受限入口缺少资源边界；还有一处 API 身份来源不一致。
这些问题不会让既有测试变红，属于"测试绿但边界假"的一类缺陷。

本轮不新增功能，只把已经声明的边界做实，并补齐可证明的反例测试。

## 2. 决策

### 2.1 设备授权只暴露只读快照

`RuntimeContainer.authorization` 不再返回原始 `DeviceAuthorizationSession`，改为返回只读快照
`RuntimeAuthorizationView`：只允许读取 `session_id` / `manifest` / `budget_state` /
`batch_index` / `closed`，**不暴露** `rotate` / `authorize` / `close`。

- 原始会话仅保存在模块级弱引用表中，视图实例上不存在可达的会话属性，
  `object.__getattribute__(view, "_session")` 也会失败；
- 容器通过受控辅助函数在 `close()` 时关闭会话，因此快照在关闭后仍可读到终态；
- Gateway 内部继续共享同一个强制预算载体，预算仍由同一对象统一消费。

结论：公开调用方无法替换 manifest、无法重置预算，也无法提前撤销会话。

### 2.2 超时：协作取消 + 严格准入闸门（**不声称**能强制终止任意代码）

`ToolLoopRunner` 越过 deadline 后不只是返回 timeout，而是置位运行级协作取消令牌
`RunCancellation`，再**有限等待**底层操作协作退出后才返回。

- 底层模型 / 工具 / Adapter 通过 `current_cancellation()` 观察取消；
- 不使用无界 join、不加大 timeout、不吞迟到结果、不使用 `Future.cancel()`；
- Python **无法抢占式终止**正在运行的线程，因此取消是**协作式契约**，不是强制手段。

保证分两层（2026-10-01 修订：收窄并准确命名）：

1. **准入闸门（严格模式，默认）**：Runner 在调用任何模型 / 工具之前，先检查参与者是否
   显式声明 `cancellation_aware = True`（见 `ports/cancellation.py`）。未声明的实现——也就是
   "不可控后台工作"——**根本不会被调用**，因此不可能在 Runner 返回后继续产生副作用。正式
   Runtime 的 `FakeLLM` 与全部工具都在 `FakeLLM` / `BaseTool` 上声明契约，并有守卫测试证明；
2. **协作取消 + 有限等待**：已声明的参与者按契约退出；迟到结果一律丢弃，绝不冒充取消。

残余风险被显式上报而不是静默接受：已声明却违约、在宽限期内未退出的实现，会让结果带上
`cancellation_confirmed=False` 与"取消未确认"文案，调用方必须把该次运行视为不可信。

**已知限制**：直接调用私有的 `_within_deadline`（绕过 `run()` 的准入闸门）仍然只是
"放弃等待"，迟到副作用仍可能发生。这是 Python 线程语义的硬约束，本 ADR 不作更强承诺。

### 2.3 评测历史必须有可持久化的可信 Head

`InMemoryHistoryHeadStore` 只在进程内有效，进程重启后必然丢失可信 Head，历史只能被判为
不受信。新增 `FileHistoryHeadStore`：把不透明 HMAC 认证标签落盘到独立文件，原子写入。

信任边界（显式声明）：只保护**同机**信任域，防的是历史文档被回滚 / 截尾 / 替换成旧快照；
能改写 Head 文件的攻击者同样能改写文档，因此它不是分布式、多副本或抗内部篡改保证。
**完整性密钥只在内存注入，绝不落盘**（也不写进锁文件或 staging 文件）；建议 Head 与历史
文档分离存放。

一个 Head 文件可同时保存多个 `history_id`，因此"多个历史文件共享同一个 Head 文件"是必须
支持的装配方式，Head 文件自身也需要跨进程互斥（见 §2.4 与 §2.8）。

### 2.4 历史写入必须跨实例串行化并可从崩溃恢复

`load → write tmp → replace → save head` 之前没有任何互斥，并发 append 会丢失更新，
且所有写者共用同一个 `.tmp` 名。决策：

- 整个 `load-modify-write` 周期置于同一把**同机排它锁**下（进程内按路径共享 `RLock` +
  跨进程 OS 文件锁），覆盖同进程多实例与同机多进程；
- staging 槽位改为确定性的 `.pending`，固定名冲突由互斥锁消除；
- 发布顺序固定为 **stage → 提交 head → 原子替换**，使两种崩溃点都收敛到一致状态：
  head 推进前崩溃则丢弃残留 pending，head 推进后崩溃则由 pending 完成发布；
- **Head 文件自己的读写也必须在它自己的跨进程锁内**（2026-10-01 补正）：历史锁是按历史
  文件路径建立的，两个不同历史文件共享同一个 Head 文件时会各自持不同的历史锁，无法保护
  Head 文件的共同读改写周期。

### 2.5 真实模型响应必须 fail closed

- `usage` 缺失或非法（非映射、缺字段、非非负整数、bool、浮点、字符串）一律拒绝
  （`missing_usage` / `invalid_usage`），**不再退化为 0 token / 0 cost**；
- 响应体字节上限 `max_response_bytes` 与正文上限 `max_content_chars`，超限即拒绝，不解析
  也不截断；其中 `max_response_bytes` 是**传输期**边界（2026-10-01 修订）：用
  `client.stream(...)` + `iter_bytes()` 逐块累计，超限立即停止读取并关闭响应，而不是先
  完整缓冲再检查；
- 仍保持每案例最多一次请求、无重试；
- 受控错误不再链式保留 httpx / JSON 原始异常，避免通过因果链泄漏响应正文、API key 或 endpoint。

### 2.6 BGE Adapter 补齐 endpoint 与资源边界

- host / scheme / port 三重 allowlist，禁止 userinfo / query / fragment，默认只允许本机
  `http://127.0.0.1:18080`；
- 限制批量条数、单条字符数、总字符数；响应字节上限改为**传输期**边界（2026-10-01 修订），
  与真实模型客户端共用 `http_stream.read_bounded_bytes`，语义一致；
- 拒绝 NaN / Infinity、字符串 / 布尔元素、错误长度、越界 / 重复 / 缺失 / 非整数 `index`；
- 稳定错误类型 `BgeEmbeddingError`（不含 endpoint / 正文 / 向量）与 `close()` / 上下文管理器；
  注入的 client 不被适配器关闭；
- **不接入正式 Runtime**：`runtime.py` 不引用该适配器，并新增守卫测试。

### 2.7 API 身份来源与职责分离

- `create_app()` 的两种模式必须**恰好二选一**：正式模式必须提供 `authenticator` 且
  `demo_mode=False`；Demo 模式必须 `authenticator is None` 且 `demo_mode=True`；两者都缺或
  同时存在都拒绝构建（2026-10-01 补正：此前允许"认证 + Demo"并存，会让已认证请求重新采用
  正文里的 reporter/reviewer）；
- `create_diagnoses_router()` 做同样的防御性校验，防止绕过工厂直接构造矛盾路由；
- actor 解析在**结构上**优先使用认证 principal：只要存在已认证主体，正文自报值就不可能
  生效，与 `demo_mode` 取值无关；
- 正式入口 `scripts/run_api.py` **即使只监听 localhost** 也要求分离的 operator/reviewer
  双凭证；无认证 Demo 只能通过显式 `SECURITY_DIAGNOSIS_API_DEMO` 开关且在回环地址开启；
- operator 不能 review，reviewer 不能创建 / 运行；同时携带双角色的 principal 两条路径都拒绝；
- 同一 actor 不能审核自己上报的诊断（`self_review_not_allowed`）。

### 2.8 2026-10-01 跟进修订摘要

对 2026-09-29 首次修复的独立复核发现 4 处"测试通过但边界未闭环"的问题，本 ADR 相应收窄表述：

| 问题 | 首次修复的实际边界 | 本次修订 |
|---|---|---|
| 超时后非协作 worker 继续运行 | 只置位协作令牌并有限等待，未声明的参与者仍会执行 | 增加严格模式准入闸门：未声明 `cancellation_aware` 的参与者**根本不执行**；违约者以 `cancellation_confirmed=False` 上报 |
| 响应大小上限 | 在完整缓冲之后检查，只阻止 JSON 解析 | 改为传输期流式限长，超限立刻停止读取并关闭响应 |
| `authenticator` + `demo_mode=True` 可并存 | 正文重新成为 actor 来源 | 两模式互斥，且 actor 结构上优先取认证 principal |
| 共享 Head 文件无跨进程互斥 | 只有进程内 `RLock`，跨进程丢更新且固定 `.tmp` 冲突 | Head 文件自己的 `.head-lock` 跨进程锁 + 唯一 staging 名 + 原子替换 |

## 3. 后果

- 优点：公开契约与实现一致；越界行为由拒绝取代静默降级；每条边界都有可执行反例。
- 代价：正式入口启动需要显式凭证配置（含本地回环），本地手工试跑需显式开 Demo；
  严格模式要求 LLM / 工具实现显式声明协作取消契约，未声明的实现会被拒绝执行（可用
  `require_cancellation_aware=False` 显式放行，仅限评测与实验）。
- 已知限制：取消仍是**协作式**的，不是任意代码的强制终止；直接调用私有
  `_within_deadline` 绕过准入闸门时无法阻止迟到副作用。
- 下一决策点：真实 LLM 正式接入（见 ADR-001 §2.3）与 BGE Vector/Hybrid 正式注入仍需
  按门禁推进；本轮只完成加固，不改变"默认 Runtime 不接外部依赖"的结论。
