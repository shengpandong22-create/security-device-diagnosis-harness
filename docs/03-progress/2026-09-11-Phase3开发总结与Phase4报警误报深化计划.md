## 1. Phase 3 阶段定位

Phase 0～2 已经证明 Harness 可以覆盖视频类设备故障：

```text
摄像头黑屏 -> 录像缺失 / 录像异常
```

Phase 3 选择“门禁刷卡异常”，不是为了堆更多接口，而是为了验证一个更关键的问题：

> 这套 Harness 是否能迁移到完全不同的安防业务域？

门禁刷卡异常涉及人、凭证、门、控制器、权限、授权时段和刷卡事件。它和摄像头实时画面、录像回放不是同一条业务链路，因此 Phase 3 的意义在于证明当前项目不是“摄像头诊断脚本”，而是一套可复用的可信诊断底座。

## 2. Phase 3 已完成内容

### 2.1 Phase 3A：门禁领域事实

新增 `domain/access.py`，把门禁诊断所需事实拆成 5 类模型：

| 模型 | 表达事实 | 诊断价值 |
|---|---|---|
| `AccessControllerSnapshot` | 控制器在线状态、健康状态、最近错误 | 判断刷卡失败是否源于控制器离线或无响应 |
| `DoorSnapshot` | 门状态、门锁状态、门锁异常 | 判断授权通过后是否因门锁/门磁异常无法开门 |
| `CredentialSnapshot` | 凭证类型、状态、有效性 | 判断卡、人脸、二维码、指纹等凭证是否冻结、过期或挂失 |
| `AccessPolicySnapshot` | 人员/凭证对门的权限、授权时段 | 判断是否无门权限或不在授权时段 |
| `AccessEvent` | 刷卡结果、拒绝原因、事件时间 | 作为门禁诊断的关键现场事实 |

安全边界：

- 卡号、人脸特征、指纹模板、PIN、手机号、身份证等字段入模型前脱敏；
- 领域模型只表达事实，不包含 `confidence`、`root_cause`、`conclusion`；
- 领域层不依赖 API、Tool、Runner、Adapter、数据库或真实模型。

关键规则口径：

- 规则不读样例 JSON；

## 3. Phase 3 的关键工程经验

### 3.1 业务事实要和敏感标识解耦

门禁场景天然包含人员、卡号、人脸、指纹等敏感信息。Phase 3 的设计没有让规则依赖原始 `person_id` 或 `credential_id`，而是依赖：

- 凭证状态；
- 授权策略是否允许；
- 刷卡事件拒绝原因；
- 控制器和门锁状态。

这让诊断系统能保留业务判断能力，同时避免把敏感标识暴露给报告或模型。

### 3.2 probable 仍然必须由多类事实支撑

门禁类 Evidence 加入 CitationPolicy 后，`probable` 依然不是“只要有一个刷卡事件就可以”。它必须至少引用两类不同设备事实，例如：

```text
access_controller + access_event
access_credential + access_policy
access_door + access_event
```

这延续了 Phase 1/2 的核心原则：知识库和单一事实只能支持较弱判断，多类现场事实才能支持更高可信度。

### 3.3 新业务域要复用 Harness，而不是复制一套系统

Phase 3 没有新增新的 Agent Loop，也没有绕开原有 ApplicationService。门禁只是新增：

```text
Domain Facts -> DeviceGateway Methods -> READ_ONLY Tools
             -> EvidenceTypes -> Rules -> Report -> Eval
```

主干仍然是：

```text
ToolRegistry -> ToolLoopRunner -> Evidence -> CitationPolicy -> HumanReview -> Report/Eval
```

这说明项目的扩展方式是“往 Harness 里增加业务域插件”，而不是每个故障域都写一套孤立脚本。

## 4. 为什么 Phase 4 选择报警误报

Phase 4 推荐进入“报警误报 / 误触发”诊断，原因是它能补齐安防运维里的另一类高频问题：

```text
有告警，但告警不一定是真的。
```

它和前面三个场景不同：

- 摄像头黑屏：设备能力缺失；
- 录像缺失：历史数据缺失；
- 门禁刷卡异常：权限/凭证/硬件链路失败；
- 报警误报：事件存在，但需要判断事件可信度。

报警误报能体现 Harness 的另一个价值：不是盲目相信告警，而是把告警事件、规则配置、环境干扰、传感器状态、复核结果组合成 Evidence，再由规则和模型在受控边界内给出候选判断。

## 5. Phase 4 建议拆分

### 5.1 Phase 4A：报警误报领域模型

只新增领域事实，不接工具、不改 Runner、不加评测。

建议模型：

| 模型 | 说明 |
|---|---|
| `AlarmRuleSnapshot` | 报警规则是否启用、灵敏度、阈值、防抖时间、布防时段 |
| `AlarmSignalSnapshot` | 传感器或算法信号值、阈值、噪声、是否稳定 |
| `AlarmEnvironmentSnapshot` | 雨雪、雾、强光、风、夜间等环境干扰 |
| `AlarmVerificationSnapshot` | 视频复核、人工复核、目标是否存在 |
| `AlarmCorrelationSnapshot` | 短时间重复告警、相邻设备告警、是否孤立事件 |

### 5.2 Phase 4B：只读工具与样例案例

新增只读工具：

| 工具 | 说明 |
|---|---|
| `alarm__query_rule` | 查询报警规则配置 |
| `alarm__query_signal` | 查询触发时的信号值与噪声 |
| `alarm__query_environment` | 查询环境干扰事实 |
| `alarm__query_verification` | 查询复核结果 |
| `alarm__query_correlation` | 查询重复/关联告警情况 |

固定样例建议覆盖：

| case_id | 候选根因 |
|---|---|
| `rule_too_sensitive` | 规则灵敏度过高或阈值过低 |
| `environment_interference` | 雨雾强光等环境干扰 |
| `sensor_noise` | 传感器噪声或抖动 |
| `verification_negative` | 视频/人工复核未发现目标 |
| `duplicate_alarm_burst` | 短时间重复告警风暴 |

## 6. Phase 4 不做什么

Phase 4 仍然不做：

- 自动关闭报警；
- 自动修改报警规则；
- 自动下发布防/撤防；
- 接真实摄像头、门禁、报警主机；
- 接真实模型批量评测；
- 数据库持久化；
- 前端页面；
- RAG。

原因很简单：报警误报涉及现场安全风险，Phase 4 只能做只读诊断和候选判断，不能把写操作混入当前 Harness。
