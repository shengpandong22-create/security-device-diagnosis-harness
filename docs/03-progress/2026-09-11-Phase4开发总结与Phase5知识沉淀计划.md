# Phase 4 开发总结与 Phase 5 知识沉淀计划

> 文档状态：阶段总结与下一阶段计划  
> 适用项目：Security Device Diagnosis Harness  
> 当前基线：Phase 0～4 已完成  

## 1. Phase 4 做了什么

Phase 4 将项目从“摄像头、录像、门禁”继续扩展到“报警误报 / 误触发”场景。它的价值不是单纯多加一个故障类型，而是验证同一套 Harness 架构能否迁移到另一个业务链路：

```text
报警规则
  -> 触发信号
  -> 环境干扰
  -> 复核结果
  -> 关联告警
  -> Evidence
  -> 候选根因
  -> CitationPolicy
  -> 人工确认
  -> 固定评测
```

完成后，项目已经覆盖四类安防运维诊断域：

| 阶段 | 诊断域 | 代表问题 | 当前能力 |
|---|---|---|---|
| Phase 1 | 摄像头黑屏 | 设备离线、通道离线、码流失败、平台拉流失败 | 已形成 5 个固定案例评测 |
| Phase 2 | 录像缺失 | 计划禁用、时间空隙、存储满、存储离线、索引缺失 | 已形成 5 个固定案例评测 |
| Phase 3 | 门禁刷卡异常 | 凭证冻结、无权限、授权时段不符、控制器离线、门锁卡滞 | 已形成 5 个固定案例评测 |
| Phase 4 | 报警误报 | 规则过敏、环境干扰、传感器噪声、复核否定、重复告警 | 已形成 5 个固定案例评测 |

## 2. Phase 4 的关键交付

### 2.1 Phase 4A：报警领域事实模型

新增 `domain/alarm.py`，把报警误报拆成五类事实：

- `AlarmRuleSnapshot`：报警规则、灵敏度、阈值、防抖、布防时段；
- `AlarmSignalSnapshot`：触发信号值、阈值、噪声等级、信号状态；
- `AlarmEnvironmentSnapshot`：雨、雾、强光、风、夜间、阴影等干扰；
- `AlarmVerificationSnapshot`：复核是否发现真实目标；
- `AlarmCorrelationSnapshot`：短时间重复告警、相邻设备关联告警。

领域模型只表达事实，不表达结论，不包含 `confidence`、`root_cause`、`conclusion`、`confirmed` 等字段。

### 2.2 Phase 4B：报警只读工具与静态样例

新增五个只读工具：

| 工具 | EvidenceType | 作用 |
|---|---|---|
| `alarm__query_rule` | `alarm_rule` | 查询报警规则配置 |
| `alarm__query_signal` | `alarm_signal` | 查询触发信号 |
| `alarm__query_environment` | `alarm_environment` | 查询环境干扰 |
| `alarm__query_verification` | `alarm_verification` | 查询复核结果 |
| `alarm__query_correlation` | `alarm_correlation` | 查询重复 / 关联告警 |

所有工具仍然满足：

- `READ_ONLY`；
- 必须拥有 `device:read`；
- 只能通过 ToolRegistry 调用；
- 参数非法、缺权限、设备或报警事实缺失时受控失败；
- 工具失败不产生 EvidenceDraft。

### 2.3 Phase 4C：报警规则、报告与评测

新增 `application/alarm_diagnosis_rules.py`，输出六类候选标签：

| 候选标签 | 判定依据 |
|---|---|
| `alarm_rule_too_sensitive` | 规则灵敏度高、阈值低或防抖时间过短 |
| `environment_interference` | 雨、雾、强光、风、夜间、阴影等环境因素 |
| `sensor_noise_or_stuck` | 信号噪声过高、卡死或缺失 |
| `verification_negative_false_alarm` | 复核未发现真实目标 |
| `duplicate_alarm_burst` | 短时间重复告警或相邻设备关联 |
| `insufficient_alarm_evidence` | 缺少关键报警事实 |

新增评测脚本：

```bash
uv run python scripts/eval_phase4_alarm_false_positive.py
```

当前固定评测结果：

```text
total=5
passed=5
label_accuracy=1.0
citation_compliance=1.0
external_model_called=false
sensitive_leak_count=0
```

## 3. Phase 4 中沉淀的开发经验

### 3.1 领域模型的派生属性不应假设会进入 Evidence payload

Phase 4C 初次评测时，`rule_too_sensitive` 和 `environment_interference` 两个案例没有命中。根因是领域模型中存在 `is_over_sensitive`、`has_interference` 等 Python 计算属性，但 `model_dump()` 默认只输出字段，不输出普通 `@property`。

因此规则层不能只依赖派生字段，而应该基于 Evidence payload 中真实存在的原始字段重新计算：

```text
sensitivity / threshold / debounce_seconds -> 是否规则过敏
interference_types                         -> 是否环境干扰
status / noise_level                       -> 是否信号异常
pattern / repeated_count                   -> 是否重复告警
```

这是一个很重要的工程经验：Evidence 是跨层边界，不应假设领域对象的运行时属性在持久化或传输后仍然存在。

### 3.2 “复核未发现目标”不能等同于 target_count=0

报警样例里有不少 `target_count=0` 且 `result=inconclusive` 的情况。它只代表“当前没有确认目标”，不代表“复核明确否定”。因此规则最终收紧为：

```text
result == no_target_found
或 indicates_false_alarm == true
```

才判定为 `verification_negative_false_alarm`。

这个取舍避免了把“重复告警风暴”误判成“复核否定误报”。

### 3.3 规则是候选解释，不是最终结论

Phase 4 继续坚持：

- 规则只产生 `candidate_label`；
- 模型只能产生 `possible/probable` 候选结论；
- `probable` 必须引用至少两类设备事实 Evidence；
- `confirmed` 只能由人工 review 产生。

这保证了项目不是“规则自动判死刑”，而是“系统提出候选、保留证据、等待人工确认”。

## 4. 当前项目已经形成的可复用扩展套路

新增一个业务诊断域时，当前最稳的扩展顺序是：

```text
1. Domain：先定义事实模型
2. EvidenceType：定义事实证据类型
3. DeviceGateway Port：定义只读采集方法
4. StaticDeviceGateway：用本地 JSON 模拟真实设备事实
5. Tool：封装为 READ_ONLY 工具
6. CitationPolicy：把该域事实纳入可信引用集合
7. Rule：基于 Evidence 输出候选标签
8. Report：展示候选根因、证据链、排查顺序和排除项
9. Eval：固定案例集验证 label、引用、脱敏和无外部调用
```

Phase 1～4 都走通了这条路线，说明 Harness 主体架构已经具备横向扩展能力。

## 5. 为什么 Phase 5 不继续增加故障域

继续增加“设备离线”“告警不上报”“视频卡顿”等场景当然可以，但边际收益开始下降。当前项目更需要从“多场景诊断”升级为“可沉淀经验的诊断系统”。

Phase 5 的核心目标是：

```text
confirmed 诊断
  -> 提取可复用经验
  -> 生成 Knowledge Candidate
  -> 人工审核
  -> 进入可检索知识库
  -> 下一次诊断可召回
```

这一步会让项目从“固定案例可跑”进一步接近真实 Agent 产品：

- 它不是每次从零开始；
- 它能把人工确认过的经验沉淀下来；
- 它能用评测验证知识引入后是否退化；
- 它为后续 RAG、向量召回和企业知识库接入留下位置。

## 6. Phase 5 建议拆分

### Phase 5A：Knowledge Candidate 领域模型

目标：先定义“知识候选”在系统中的领域边界。

交付：

- `KnowledgeCandidate`；
- `KnowledgeCandidateStatus`；
- `KnowledgeCandidateSource`；
- `KnowledgeReview`；
- 状态机与人工审核边界；
- 敏感字段脱敏；
- 领域测试。

不做：

- 不接数据库；
- 不改 `knowledge__search`；
- 不做向量库；
- 不调用真实模型；
- 不自动把 candidate 变 confirmed。

### Phase 5B：confirmed 诊断生成知识候选

目标：在人工确认诊断后，生成可审核的知识候选。

交付：

- 从 confirmed `SecurityDiagnosisCase` 提取候选知识；
- 保留原始 Diagnosis、Conclusion、Evidence 引用；
- 输出故障类型、候选标签、根因摘要、排查步骤；
- 不保存完整敏感 payload；
- 候选知识仍需人工审核。

### Phase 5C：轻量知识检索与 RAG 演进入口

目标：让 `knowledge__search` 不再只是硬编码静态 SOP，而是可以检索人工确认后的知识。

交付：

- 轻量内存或 JSON 知识库；
- `knowledge__search` 契约保持不变；
- confirmed knowledge 可被下次诊断召回；
- 固定 eval 验证 Phase 1～4 不退化；
- 为后续 SQLite / 向量库 / BGE / RAG 留接口。

## 7. Phase 5 的验收方向

Phase 5 的验收不只看功能跑通，还要看是否守住边界：

- 模型不能直接写入 confirmed knowledge；
- 自动提取只能产生 candidate；
- candidate 必须人工 review 后才能 confirmed；
- confirmed knowledge 必须可追溯到原始 Diagnosis 与 Evidence；
- 知识内容不能泄露密码、Token、人员标识、截图 URL；
- 引入知识检索后，Phase 1～4 固定评测不能退化。

## 8. 一句话总结

Phase 4 证明了 Harness 可以横向扩展到更多安防业务域；Phase 5 则要证明系统可以纵向形成经验沉淀闭环，从“会诊断”走向“会积累”。
