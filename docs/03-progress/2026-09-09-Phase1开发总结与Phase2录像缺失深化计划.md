## 1. 阶段定位

Phase 0 已经完成了安防设备诊断 Harness 的最小闭环：

```text
创建诊断 -> 只读工具采集设备事实 -> Evidence 留存 -> 候选结论
        -> Citation Policy 校验 -> 人工确认/驳回 -> Markdown 报告
```

Phase 1 没有急着接真实设备或真实模型，而是选择把第一个业务场景“摄像头黑屏”做深。这样做的目的有两个：

1. 验证 Harness 能不能承载真实安防诊断逻辑，而不是只停留在通用 Agent Demo；
2. 通过固定案例集和评测脚本，把“诊断是否正确”变成可回归验证的工程指标。

因此，Phase 1 的价值不在于新增了多少代码，而在于它把项目从“通用诊断骨架”推进到了“可解释、可评测的具体安防故障域”。

## 2. Phase 1 已完成内容

### 2.1 摄像头黑屏事实模型

新增 `domain/camera.py`，用安防业务事实表达摄像头黑屏相关状态：

| 模型 | 表达内容 | 诊断价值 |
|---|---|---|
| `ChannelSnapshot` | 通道在线状态、绑定状态、最后错误 | 判断平台是否还能访问设备通道 |
| `StreamSnapshot` | 主/子码流、分辨率、码率、编码状态 | 判断设备侧是否能正常推流或编码 |
| `PlatformPullStatus` | 平台拉流状态、失败原因、耗时 | 判断黑屏是否发生在平台拉流链路 |

这些模型和 Phase 0 的 `DeviceSnapshot`、`DeviceAlarmEvent`、`DeviceConfigSnapshot` 一起构成摄像头黑屏诊断的事实基础。

### 2.2 DeviceGateway 与只读工具扩展

Phase 1 扩展了 DeviceGateway Port 和 Static Adapter，并新增三个只读工具：

| 工具 | 类型 | 采集事实 |
|---|---|---|
| `device__query_channel` | READ_ONLY | 通道状态 |
| `device__query_stream` | READ_ONLY | 码流状态 |
| `platform__query_pull_status` | READ_ONLY | 平台拉流结果 |

关键原则没有变化：

- 所有工具必须经过 `ToolRegistry`；
- 工具失败不能伪造成 Evidence；
- 所有工具仍然是 READ_ONLY；
- 真实设备访问仍然没有接入。

### 2.3 摄像头黑屏候选根因规则

新增 `application/camera_diagnosis_rules.py`，用于把多类 Evidence 汇总成候选根因：

| 候选标签 | 判断依据 |
|---|---|
| `device_offline_or_network_unreachable` | 设备离线或不可达 |
| `channel_binding_or_platform_access_issue` | 设备在线但通道离线 / 绑定异常 |
| `stream_publish_or_encoder_issue` | 通道在线但码流发布失败 |
| `overloaded_encoding_configuration` | 高码率 / 高分辨率导致编码压力过大 |
| `platform_pull_or_access_path_issue` | 设备侧基本正常，但平台拉流失败 |

这里要注意一个边界：规则只产生 `candidate_label`，不会产生 `confirmed`。最终确认仍然必须由人工审核完成。

## 3. Phase 1 固定案例集

Phase 1 当前覆盖 5 个摄像头黑屏子场景：

| case_id | 故障现象 | 期望候选根因 |
|---|---|---|

这些案例的意义是：不用真实设备，也可以稳定复现典型安防诊断分支，便于持续回归。

## 4. 本阶段关键修复经验

### 4.1 问题：probable 引用补齐逻辑存在边界漏洞

Phase 1 初版中，`repair_cited_evidence_ids` 的逻辑是：

```python
merged = list(dict.fromkeys([*kept, *needed]))[
    : max(len(needed), MIN_DEVICE_FACT_TYPES_FOR_PROBABLE)
]
```

在以下场景会出错：

```text
已引用：knowledge_sop + device_status
Case 中已有：knowledge_sop + device_status + device_alarm
期望：补入 device_alarm，维持 probable
实际：合并后切片可能把 device_alarm 裁掉
```

结果就是：结论仍然是 `probable`，但只引用了一类设备事实 Evidence。这违反了 Phase 1 的 Citation Policy：`probable` 至少需要两类设备事实。

### 4.2 修复：按“缺失设备事实类型”补齐

修复后的思路是：

```text
1. 保留模型已有的合法引用；
2. 统计已有引用中覆盖了哪些设备事实类型；
3. 只补充缺失类型；
4. 补齐后再次确认是否满足 probable；
5. 仍不足时降级为 possible。
```

这样可以保证：

- `knowledge_sop` 不会挤占设备事实引用名额；
- 合法原始引用不会丢失；
- `probable` 不会在设备事实不足时被放行；
- 设备事实不足时系统会降级，而不是伪装成高可信。

### 4.3 开发经验沉淀

这次问题说明：Agent 项目中的 Citation 修复不能只看“引用数量”，还要看“引用类型是否满足可信度要求”。

尤其在诊断场景中，知识库 SOP 只能提供参考，不能替代现场事实。一个结论如果要达到 `probable`，必须至少引用足够的设备事实，否则就应该保持 `possible` 或 `inconclusive`。

这也是 Harness 和普通“把日志/现象丢给大模型”的区别：模型可以提出判断，但可信度升级必须经过确定性规则约束。

## 6. 为什么 Phase 2 选择录像缺失 / 录像异常

Phase 2 推荐进入“录像缺失 / 录像异常”，原因是它和摄像头黑屏有天然连续性：

```text
摄像头黑屏关注：能不能看实时画面
录像缺失关注：历史录像是否按计划产生、保存、可回放
```

两者共享很多底层事实：

- 设备是否在线；
- 通道是否在线；
- 码流是否正常；
- 平台是否能访问设备；
- 配置是否异常。

但录像缺失又会引入新的诊断事实：

- 录像计划是否启用；
- 录像时间段是否覆盖；
- 存储池是否可用；
- 磁盘容量是否不足；
- 回放索引是否存在；
- 录像文件是否可读取。

因此 Phase 2 既能复用 Phase 1 的能力，又能证明 Harness 可以扩展到第二类业务故障域。

## 7. Phase 2 建议拆分

### 7.1 Phase 2A：录像诊断领域模型

目标：先建立录像缺失诊断所需的领域事实，不接工具、不改 Agent Loop。

建议新增：

| 模型 | 说明 |
|---|---|
| `RecordingPlanSnapshot` | 录像计划是否启用、计划时间段、计划类型 |
| `StorageSnapshot` | 存储池状态、总容量、剩余容量、错误信息 |
| `PlaybackCheckResult` | 指定时间段是否存在录像、是否可回放、失败原因 |

建议新增枚举：

| 枚举 | 示例 |
|---|---|
| `RecordingPlanStatus` | enabled / disabled / misconfigured |
| `RecordingMode` | continuous / event_triggered / manual |
| `StorageStatus` | normal / full / offline / degraded |
| `PlaybackStatus` | available / missing / corrupted / index_missing |

验收重点：

- 领域模型只依赖标准库与 pydantic；
- 凭证类字段继续脱敏；
- 时间段必须能表达；
- 录像计划、存储、回放结果可以组合表达录像缺失事实；
- 不新增 API、工具、数据库、真实设备访问。

### 7.2 Phase 2B：只读工具与样例案例

目标：让 Agent Harness 可以通过工具采集录像相关事实。

建议新增工具：

| 工具 | 说明 |
|---|---|
| `recording__query_plan` | 查询通道录像计划 |
| `storage__query_status` | 查询录像存储状态 |
| `recording__check_playback` | 检查指定时间段录像是否可回放 |

建议固定案例：

| case_id | 典型原因 |
|---|---|
| `recording_plan_disabled` | 录像计划未启用 |
| `recording_schedule_gap` | 查询时间不在计划时间段 |
| `storage_full` | 存储空间不足 |
| `storage_offline` | 存储池离线 |
| `playback_index_missing` | 录像存在但索引缺失 |

## 8. Phase 2 不做什么

Phase 2 暂时不要做：

- 真实 NVR / CVR / 录像平台对接；
- 自动配置修复；
- 删除、移动、修复录像文件；
- 数据库持久化；
- 前端页面；
- 大规模真实模型评测；
- 多租户权限系统。

理由：当前项目还处于个人电脑可控演示阶段，优先把第二个业务故障域做完整，比提前接真实基础设施更有价值。
