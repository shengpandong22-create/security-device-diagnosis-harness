# 2026-09-09：Phase 0 开发总结与 Phase 1 摄像头黑屏深化计划

> 项目：Security Device Diagnosis Harness
> 阶段状态：Phase 0A～0C 已完成、已验收、已推送
> 当前远程提交：`88e4e74`

## 1. 阶段结论

Phase 0 已经完成一个最小但完整的安防设备诊断 Harness 闭环：

```text
用户创建摄像头黑屏诊断
  -> 应用服务启动受控 ToolLoopRunner
  -> FakeLLM 请求只读设备工具
  -> Tool Registry 校验权限、风险、参数和白名单
  -> StaticDeviceGateway 读取本地设备样例
  -> 工具结果产生 EvidenceDraft
  -> ApplicationService 落成正式 DiagnosisEvidence
  -> ConclusionDraft 修正为真实 Evidence ID
  -> CitationPolicy 校验引用可信度
  -> Case 进入 waiting_for_confirmation
  -> 人工 confirm
  -> Case 进入 confirmed
  -> 输出 Markdown 报告
```

这说明项目的第一阶段目标成立：它不是“把设备故障描述丢给大模型”，而是把模型放进一个可控 Harness 中，由确定性工程层负责事实、权限、证据、引用、状态和人工确认。

## 2. Phase 0A：工程骨架与领域模型

Phase 0A 解决的是“项目有没有一个干净的安防设备诊断领域起点”。

已完成内容：

| 模块 | 完成内容 |
|---|---|
| Python 工程骨架 | `pyproject.toml`、`uv.lock`、`src/`、`tests/`、`scripts/`、`samples/` |
| FastAPI 最小入口 | `GET /health` |
| 诊断领域 | `SecurityDiagnosisCase`、`SecurityFaultType`、`SecurityDiagnosisStatus` |
| 设备事实 | `Device`、`DeviceSnapshot`、`DeviceAlarmEvent`、`DeviceConfigSnapshot` |
| 证据与结论 | `DiagnosisEvidence`、`DiagnosisConclusion` |
| 人工审核 | `HumanReview`、`HumanReviewAction` |
| 状态边界 | `confirmed` 只能由人工 confirm 产生 |
| 安全底线 | 配置凭证字段提前脱敏 |

Phase 0A 中曾发现并修复一个关键问题：

```text
SecurityDiagnosisCase.add_evidence 遇到重复 hash 时，原先返回新传入但未挂接的 Evidence。
```

该问题会导致后续结论引用未保存的 Evidence ID。修复后，重复 Evidence 返回 Case 中已存在的 Evidence，并补充了回归测试。

开发经验沉淀：

> Evidence 去重不能只关注“列表长度不增加”，还要关注“返回对象是否可被后续链路引用”。在 Agent 系统里，Evidence ID 会被模型结论、报告和评测继续使用，返回值语义必须稳定。

## 3. Phase 0B：Harness 与只读工具基础

Phase 0B 解决的是“LLM 怎样被约束在设备事实采集流程里”。

已完成内容：

| 模块 | 完成内容 |
|---|---|
| LLM Port | `LLMClient`、`LLMRequest`、`LLMResponse`、`ToolCall`、`ConclusionDraft` |
| Fake LLM | 预设响应 / responder 模式，不访问网络 |
| DeviceGateway Port | `query_status`、`search_alarm_events`、`read_config_snapshot` |
| StaticDeviceGateway | 从本地 JSON 读取设备状态、告警、配置 |
| Tool Contract | 风险等级、权限、上下文、结果、EvidenceDraft |
| Tool Registry | 注册、重复拒绝、未知拒绝、权限校验、故障类型校验、参数校验 |
| 只读设备工具 | `device__query_status`、`device__search_alarm_events`、`device__read_config_snapshot` |
| 知识工具 | `knowledge__search` 最小静态 SOP |
| Runner | 最小受控 Tool Loop，带轮次和工具调用预算 |
| CitationPolicy | 校验结论 Evidence 引用和可信度 |

Phase 0B 中质量闸门卡住过一个问题：

```text
CitationPolicy 曾允许 possible 结论零引用 Evidence。
```

这个口径被收紧为：

| 结论等级 | 引用要求 |
|---|---|
| `possible` | 至少引用一条 Evidence，可以只引用 `knowledge_sop` |
| `probable` | 至少引用一条设备事实 Evidence：`device_status` / `device_alarm` / `device_config` |
| `confirmed` | 不允许模型产生，只能由人工 Review 产生 |

开发经验沉淀：

> 如果允许模型在零证据情况下输出 possible，项目就会退化成普通 Demo。可信诊断 Harness 的最低门槛是：任何候选结论都必须可追溯到至少一条证据。

## 4. Phase 0C：API、应用闭环、报告与 Demo

Phase 0C 解决的是“已有领域和 Harness 能否真正串成一条可运行链路”。

已完成内容：

| 模块 | 完成内容 |
|---|---|
| 内存仓储 | `InMemoryDiagnosisRepository`，纯 dict + 深拷贝 |
| 应用服务 | `SecurityDiagnosisApplicationService` |
| Evidence 落地 | `ToolEvidenceDraft -> DiagnosisEvidence` |
| 引用修正 | 空引用草稿修正为真实 Evidence ID |
| CitationPolicy 硬闸门 | 结论落地前必须校验 |
| 诊断 API | create / get / run / evidence / review / report |
| 人工 Review | confirm / reject / request_more_info |
| Markdown 报告 | 展示基本信息、结论、Evidence、人工审核 |
| Demo | `scripts/demo_phase0_camera_black_screen.py` |

Demo 验收输出示例：

```json
{
  "status": "confirmed",
  "evidence_count": 4,
  "conclusion_confidence": "probable",
  "human_action": "confirm",
  "external_model_called": false
}
```

4 条 Evidence 分别来自：

1. `device_status`：设备在线但码流 abnormal；
2. `device_alarm`：存在 `STREAM_PUBLISH_FAILED` 告警；
3. `device_config`：设备配置快照，凭证字段已脱敏；
4. `knowledge_sop`：摄像头黑屏排查 SOP。

开发经验沉淀：

> Runner 不直接改 Case 状态、不直接落 Evidence、不直接 confirmed。ApplicationService 才是用例编排和状态推进边界。这样可以让 Agent 失败、工具失败、模型空输出都被确定性代码收敛。

## 6. 当前项目边界

Phase 0 完成的是最小闭环，不是完整产品。

当前明确没有做：

- 真实设备网关；
- 真实视频流检测；
- 数据库持久化；
- 真实 LLM Client；
- 多设备、多场景评测；
- 写操作工具；
- 人工审批流；
- 工单系统；
- 企业权限系统；
- 向量数据库或真实 RAG。

这不是缺陷，而是阶段性边界。

面试时应这样表达：

> Phase 0 的目标不是做一个完整安防运维平台，而是验证 Harness 架构是否成立：模型只能在只读工具、Evidence、CitationPolicy 和人工确认约束下给出候选结论。

## 7. Phase 1 为什么聚焦“摄像头黑屏深化”

下一阶段不建议马上扩展门禁、报警、录像缺失等多个场景。

原因：

1. 当前摄像头黑屏已经有最小闭环，但诊断深度还偏浅；
2. 面试展示需要一个讲得深、跑得通、证据链完整的标杆案例；
3. 如果过早铺多个设备域，容易变成样例堆砌；
4. 摄像头黑屏最贴近安防业务，能自然引出设备状态、通道、码流、告警、配置、平台拉流等概念。

Phase 1 的目标应该是：

> 把“摄像头黑屏”从单一 demo 深化为一个可解释、可评测、可对比的诊断样板场景。

## 8. Phase 1 建议拆分

### Phase 1A：摄像头黑屏事实模型深化

目标：让摄像头黑屏不只是 `stream_status=abnormal`，而是能表达更细的设备事实。

建议新增或扩展：

| 模型 | 说明 |
|---|---|
| `ChannelSnapshot` | 通道在线、绑定摄像头、平台接入状态 |
| `StreamSnapshot` | 主/子码流、编码格式、码率、分辨率、帧率、取流状态 |
| `RecordingPlanSnapshot` | 是否启用录像、计划时间段、存储状态 |
| `PlatformPullStatus` | 平台拉流成功/失败、错误码、最近失败时间 |

验收标准：

- 摄像头黑屏至少能区分设备离线、通道异常、码流异常、配置异常、平台拉流失败；
- 每类事实都能转成 Evidence；
- 仍然不访问真实设备。

### Phase 1B：摄像头黑屏诊断策略深化

目标：让诊断结论不只是固定 `STREAM_PUBLISH_FAILED`，而是能根据证据组合区分不同根因候选。

建议规则：

| 事实组合 | 候选结论 |
|---|---|
| 设备离线 | 设备离线或网络不可达 |
| 设备在线 + 通道离线 | 通道绑定或接入异常 |
| 设备在线 + 码流异常 + 编码告警 | 编码器或码流发布异常 |
| 码率过高 + 编码超时 | 配置过高导致编码压力 |
| 设备正常 + 平台拉流失败 | 平台侧接入或拉流链路异常 |

验收标准：

- 至少 4 个摄像头黑屏子案例；
- 每个子案例输出不同候选根因；
- probable 结论至少引用两类设备事实 Evidence；
- 只引用 SOP 的结论只能是 possible。

### Phase 1C：摄像头黑屏评测集

目标：把 Phase 0 的单 demo 变成可回归的固定案例集。

建议案例：

| case_id | 场景 | 期望 |
|---|---|---|
| `camera_offline` | 设备离线 | 根因候选为设备离线或网络不可达 |
| `stream_publish_failed` | 设备在线但码流发布失败 | 根因候选为码流/编码异常 |
| `high_bitrate_encoder_timeout` | 高码率导致编码超时 | 根因候选为配置过高 |
| `platform_pull_failed` | 设备正常但平台拉流失败 | 根因候选为平台接入链路异常 |

验收标准：

- 提供 `scripts/eval_phase1_camera_black_screen.py`；
- 输出每个案例的命中情况；
- 输出 Markdown/JSON 评测报告；
- 默认 Fake LLM，不调用真实模型；
- 可选真实模型低频评测脚本必须单独提供，且需显式环境变量开启。

### Phase 1D：报告和面试材料增强

目标：让项目更好讲。

建议增强：

- 报告中增加“证据链解释”；
- 增加“为什么不是其他根因”；
- 增加“建议排查顺序”；
- 增加 Phase 1 架构图；
- 增加摄像头黑屏时序图；
- 增加面试 Q&A。

验收标准：

- 报告可以让不了解代码的人理解诊断依据；
- 面试时能用 3 分钟讲清“设备事实 + Evidence + Harness 约束”；
- 图和文档不暗示已经接入真实设备。

## 9. Phase 1 禁止事项

Phase 1 仍然不建议做：

- 真实摄像头接入；
- RTSP 拉流；
- 设备重启；
- 配置下发；
- 门禁/报警/录像缺失全面扩展；
- 数据库持久化；
- LangGraph 多 Agent；
- 模型微调；
- 企业权限系统。

原因：

> Phase 1 应该先把一个业务场景讲深，而不是把多个业务场景讲浅。

## 10. Phase 1 给其他模型的开发边界

后续给其他模型的提示词应该强调：

```text
只深化摄像头黑屏，不扩展门禁、报警和录像缺失。
只扩展设备事实模型、样例数据、诊断策略、评测脚本和报告表达。
不接真实设备、不接数据库、不调用真实模型。
所有结论必须继续通过 Evidence 和 CitationPolicy。
```

## 11. 面试表达升级

Phase 0 可以这样讲：

> 我先做了一个安防设备诊断 Harness 的最小闭环，证明模型不是自由发挥，而是在只读设备工具、Evidence、CitationPolicy 和人工确认约束下完成候选诊断。

Phase 1 做完后，可以升级为：

> 在摄像头黑屏场景里，我进一步拆分了设备离线、通道异常、码流异常、编码配置过高、平台拉流失败等子场景。系统会根据设备状态、告警事件、配置快照和 SOP 形成证据链，再由 Harness 校验结论可信度。这样不是简单回答“摄像头黑屏怎么办”，而是能基于不同事实组合给出不同根因候选和排查顺序。
