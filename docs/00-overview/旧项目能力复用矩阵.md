# 旧项目能力复用矩阵

> 目的：明确新项目参考 `application-diagnosis-platform` 的哪些工程经验，禁止把哪些应用日志诊断内容照搬进安防设备诊断域。

## 1. 总原则

新项目采用：

```text
工程机制复用，业务领域重建
```

也就是说，可以参考旧项目里已经验证过的 Harness 思想，但安防设备的领域对象、工具、证据类型、故障样例和面试叙事必须重新设计。

## 2. 复用矩阵

| 新项目模块 | 旧项目参考 | 复用方式 | 禁止照搬内容 | 验收要求 |
|---|---|---|---|---|
| LLM Client Port | `ports/llm.py` | 参考供应商无关接口，支持 Fake LLM 与 OpenAI-compatible LLM | 不继承旧项目 Prompt 和应用故障结论 Schema | 自动测试默认 Fake LLM；真实模型调用必须显式脚本触发 |
| Tool Contract | `tools/contracts.py` | 参考结构化输入输出、工具风险、权限声明 | 不保留 `code__search`、`code__read` 作为主线工具 | 每个工具必须声明权限、风险、超时和支持的故障类型 |
| Tool Registry | `tools/registry.py` | 参考注册、白名单、参数校验、权限校验 | 不允许工具绕过 Registry 被直接调用 | 未注册工具、无权限工具、参数非法工具必须被拒绝 |
| ToolLoopRunner | `agent/runner.py` | 参考“LLM 决策 + 确定性闸门 + 工具结果回传”的循环思想 | 不照搬应用日志上下文构造和 Java 源码工具流程 | Runner 不直接修改领域状态，只返回运行结果 |
| Evidence | `domain/evidence/` | 参考证据 ID、hash、reliability、redaction、source_reference | 不迁移 `log_excerpt` 作为主线，不迁移 `code_excerpt` | 设备状态、告警、配置、SOP 必须能转为 Evidence |
| Citation Policy | `domain/evidence/citation_policy.py` | 参考结论引用校验和可信等级控制 | 不引用旧项目 Java 代码 Evidence | probable 至少引用设备事实 Evidence；只引用知识最多 possible |
| Redaction | `redaction` 相关模块 | 参考入库前脱敏和模型前脱敏 | 不保存真实设备密码、Token、连接串 | IP、Token、password、secret 样例不得原样入库 |
| Confirmation | `domain/confirmation/` | 参考人工确认、驳回、继续调查 | 不允许模型产生 confirmed | confirmed 必须追加人工记录，不覆盖原始结论 |
| Knowledge Candidate | confirmed 后知识候选生成 | 参考从确认结论沉淀知识候选 | 不复用 NPE、连接池等应用知识 | 摄像头黑屏等 confirmed 案例可生成 candidate |
| Eval Harness | `evaluation/` | 参考固定案例集、Rubric、回归报告 | 不复用 Java Lab 案例 | Phase 0 至少有摄像头黑屏固定案例 |
| Report | 报告生成模块 | 参考 Markdown 报告结构 | 不保留应用日志诊断术语为主线 | 报告必须显示证据、结论可信度、建议动作和人工状态 |
| Audit Event | 审计事件模块 | 参考动作摘要和安全摘要 | 不保存完整敏感配置和凭证 | 记录设备工具调用、人工反馈、知识候选创建 |
| Service Catalog | 旧项目 Phase 3C | 只参考“资源受限上下文”的思想 | 不把 Gateway/Nacos/Trace 作为新项目主线 | 新项目用 Device Registry 表达设备、通道、区域、能力 |
| Java Lab | 旧项目 Phase 1 | 不复用 | 禁止迁移 Spring Boot/NPE/源码诊断样例 | 新项目样例必须是安防设备故障 |

## 3. 新项目优先设备工具

Phase 0 优先实现三个只读工具：

| 工具名 | 用途 | Evidence 类型 |
|---|---|---|
| `device__query_status` | 查询设备在线、通道、码流、录像状态 | `device_status` |
| `device__search_alarm_events` | 查询设备告警、上下线、异常事件 | `device_alarm` |
| `device__read_config_snapshot` | 读取设备配置快照 | `device_config` |

这些工具只能从 `StaticDeviceGateway` 读取本地样例数据。未来接真实设备平台时替换 Adapter，不改 Harness 主流程。

## 4. 必须保留的边界

- LLM 不能直接访问任意文件、任意网络或任意设备；
- LLM 不能直接改变设备状态；
- LLM 不能直接把结论标记为 confirmed；
- 工具失败不能被包装成成功证据；
- 设备不在线、告警存在、配置异常都只能构成根因候选，不能自动等于根因；
- 知识库 SOP 只能提供经验依据，不能替代现场事实。

## 5. 面试表达

> 旧项目给我沉淀的是 Agent Harness 的工程方法，新项目重建的是安防设备诊断业务域。我没有把 Java 服务日志诊断搬过来，而是把 Tool Registry、Evidence、Citation Policy、Confirmation、Eval 这些通用约束机制迁移到设备状态、告警事件、配置快照和 SOP 诊断场景里。
