# 长会话上下文膨胀与任务接力复盘

## 1. 为什么记录这个问题

本项目从 Phase 0 演进到 Phase 11，期间在同一条 Codex 会话中混合了需求讨论、架构设计、
代码实现、测试输出、外部审计、双 Agent 实验和面试准备。长会话带来了连续性，但也出现了
明显的效率拐点：一次上下文整理后，窗口仍占用较大；继续完成两个中等规模修复后，界面显示
的上下文占用从约 53% 上升到约 78%。

这两个百分比是 **2026-09-16 本项目会话中的界面观察值**，不是 token 账单，也不能直接
换算为五小时额度消耗。Codex 桌面端没有向本项目提供逐次 input/output token 明细，因此本文
不声称“占用提高 25 个百分点就等于额度多消耗多少”。

本文要解决的不是如何把一条聊天无限延长，而是：

> 如何在保留工程连续性的同时，把长期状态从聊天上下文迁移到可版本化、可审核的项目资产中。

## 2. 已确认事实、项目观察与合理推断

### 2.1 官方资料能够确认的内容

OpenAI 的模型指南将 compaction 描述为对既有会话状态的 loss-aware compression：它会保留
任务相关信息并降低上下文占用，用于多步骤、工具密集和超长对话的继续执行。官方同时建议：

- 监控上下文使用量；
- 在重要里程碑之后进行整理，而不是每一轮都整理；
- 恢复任务时保持提示词功能一致，降低行为漂移；
- 把压缩结果视为不透明的延续状态，不依赖其内部结构。

来源：<https://developers.openai.com/api/docs/guides/latest-model#4-compaction-extending-effective-context>

这说明 compaction 的目标是“继续工作”，不是“恢复成一条全新空会话”。

### 2.2 本项目直接观察到的内容

- 会话累计了大量用户需求、交付报告、审计全文、命令输出和阶段决策；
- 自动整理后仍保留了较大的上下文占用；
- 整理后继续执行两个中等修复，窗口从约 53% 增长到约 78%；
- 越到后期，模型需要同时维护的旧约束、提交记录和未完成清单越多；
- 大段粘贴外部报告和全量测试日志，会显著扩大近期上下文。

### 2.3 当前无法确认的内容

- 桌面端百分比对应多少实际 input token；
- 自动整理前后每次调用的准确 token 差值；
- 五小时额度是否按 input、output、推理时间或混合指标扣减；
- prompt cache 在当前桌面会话中的命中率和实际折扣。

因此只能说“长上下文很可能增加单次调用需要处理的输入”，不能仅凭 53%→78% 证明额度
按同样比例加速消耗。

## 3. 为什么整理后仍然很大

长会话的有效状态不只有聊天正文，至少包含四类内容：

1. **稳定指令**：系统约束、工具协议、安全规则和工作区信息；
2. **压缩历史**：旧需求、关键决定、已完成工作和未完成工作被重新编码为摘要；
3. **近期原文**：最近若干轮用户消息、代码差异和工具输出通常仍需保留细节；
4. **当前任务材料**：正在审核的源码、测试失败、补丁和验证证据。

compaction 主要压缩第二类，但不会消灭第一类，也不能过度压缩仍在使用的第三、第四类。
如果整理后立刻粘贴一份大型审计报告，再执行多轮源码读取和测试，窗口会很快再次增长。

所以“自动整理发生了”与“上下文接近空白”不是同一件事。

## 4. 本次流程暴露的反模式

### 4.1 把聊天当成项目数据库

Phase、验收结果、审计结论和后续计划长期只存在于对话中，迫使每次调用携带越来越多历史。
正确的长期真相应在 Git、ADR、验收文档和测试中；聊天只负责当前决策和临时协调。

### 4.2 在同一线程混合不同生命周期

同一会话同时承担：

- 产品讨论；
- 架构决策；
- 实现；
- 代码审查；
- 外部模型协作；
- 面试叙事；
- 题外研究。

这些任务需要的历史集合不同。混在一起会让每个后续任务都背负无关上下文。

### 4.3 把机器输出完整搬进对话

完整 pytest 日志、长交付报告和大段 diff 适合保存为文件。对话中通常只需：退出码、失败项、
关键指标和文件路径。重复粘贴相同背景不会增加工程证据，只增加输入负担。

### 4.4 把“连续会话”误认为“连续工程”

工程连续性真正来自：干净工作区、原子提交、测试、文档和明确的下一步。只要这些状态已经
落盘，新会话并不等于从头开始。

## 5. 推荐的线程生命周期

以后将一个长工程拆成四种线程，而不是按“项目只有一条聊天”组织：

| 线程类型 | 主要输入 | 结束条件 |
| --- | --- | --- |
| 设计线程 | 当前问题、约束、相关 ADR | 规格和验收边界落盘 |
| 实现线程 | 规格、起始 commit、允许文件 | 原子提交与局部测试完成 |
| 审计线程 | 固定 commit、审计维度、测试证据 | Findings 和优先级落盘 |
| 发布线程 | 提交范围、全量门禁、已知边界 | 回归报告与推送指令完成 |

一个线程完成自己的职责后就结束。新线程通过仓库文档和 commit 接力，而不是依赖聊天全文。

### 5.1 建议主动换线程的信号

满足任一条件即可考虑换线程：

- 完成一个 Phase 或一次严格审计；
- 已形成可独立提交的原子闭环；
- 主题从开发切换为面试、研究或流程复盘；
- 粘贴了大型外部报告后已经完成核验；
- 上下文界面持续处于高位，且后续还有多个中等任务；
- 连续出现两次自动整理；
- 模型开始重复读取已完成事实或混淆过期状态。

百分比不是硬门槛。重点是“旧上下文对下一任务的价值是否高于它的携带成本”。

## 6. 最小接力协议

新线程只需要下面六类信息：

```text
仓库绝对路径：
当前分支与 HEAD：
工作区是否干净：
已完成提交（只列与本任务有关的）：
下一项唯一目标：
验证纪律与禁止事项：
```

示例：

```text
仓库：D:\AgentStudy\security-device-diagnosis-harness
分支：main
起始 HEAD：add70ff
工作区：干净
已完成：confirmed 不变量、统一仓储脱敏、一致性审计扩展
下一项：授权预检与强制预算载体接入 RoutedDeviceGateway
纪律：局部测试、原子提交、不访问外部网络、不 push；全量回归留到全部修复结束
```

接手 Agent 必须先用 `git status -sb` 和 `git log --oneline -8` 验证，而不是无条件相信提示词。

## 7. 应该保存在哪里

| 信息 | 正确载体 |
| --- | --- |
| 架构为什么这样设计 | ADR / 实施规格 |
| 当前实现是否满足要求 | 自动测试 / 验收标准 |
| 发现过哪些问题 | 审计报告 |
| 已经修改了什么 | Git 原子提交 |
| 下一步做什么 | 短交接文档 / Issue |
| 一次命令的完整原始输出 | 日志文件或 CI Artifact |
| 临时讨论和权衡 | 当前会话 |

原则是：**仓库是长期记忆，会话是工作内存。**

## 8. 对 Codex + CodeBuddy 协作的进一步启示

双 Agent 编排曾关注轮询和审核成本，但长上下文本身也是成本来源：

- Codex 不应携带 CodeBuddy 的完整执行日志，只接收结构化完成事件；
- CodeBuddy 交付应写入 `RESULT.json`、提交和测试报告，而不是长篇对话；
- Codex 审核应使用新会话，输入固定 commit、规格、文件清单和短摘要；
- 返修最多一次，继续在原 worktree，避免重新加载整个项目历史；
- 小任务直接由 Codex 完成，避免为了委派协议制造比代码更大的上下文。

这与双 Agent 经济性实验的结论一致：协作的价值来自任务路由和证据压缩，不来自让两个模型
持续聊天。

## 9. 后续如何量化，而不是凭感觉

未来每个真实任务记录：

- `thread_id` / `task_id`；
- 开始和结束时界面上下文百分比；
- 自动整理次数；
- Codex 可获得的 input/output token（拿不到就明确写不可得）；
- 工具调用次数；
- 成功提交数；
- 返工次数；
- cost per successful atomic commit。

对照实验只改变一个变量：同类任务分别使用“旧长线程”和“新线程 + 最小接力协议”。在没有
逐次 token 数据时，上下文百分比只能作为辅助观测，不能冒充精确成本。

## 10. 本次经验的最终结论

1. compaction 延长了会话寿命，但不能代替任务分段；
2. 自动整理后仍占用较大空间并不矛盾，因为关键历史和近期工作仍需保留；
3. 超长项目应在里程碑处主动结束线程，而不是等上下文被动溢出；
4. 原子提交、ADR、验收测试和审计报告共同构成比聊天记录更可靠的工程记忆；
5. 新线程不是丢失上下文，而是把上下文从“全部历史”缩减为“完成下一任务所需的最小充分集”；
6. 以后优化目标不应只是减少 token，而应是降低每个成功原子闭环的上下文成本。

> 长会话擅长维持短期连续推理；Git 与文档才适合承担长期工程记忆。
