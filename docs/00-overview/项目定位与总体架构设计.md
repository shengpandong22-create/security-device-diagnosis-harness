# 项目定位与总体架构设计

## 1. 为什么要做这个项目

安防设备运维中的常见故障并不只是“看一段日志”就能解决。摄像头黑屏、录像缺失、门禁刷卡异常、报警误报这类问题，往往同时涉及设备在线状态、通道状态、码流状态、告警事件、配置快照、平台接入状态和人工巡检反馈。

普通大模型 Demo 的链路通常是：

```text
用户粘贴现象或日志 -> Prompt -> LLM -> 自然语言答案
```

这个链路最大的问题是：结论缺少证据边界，模型容易把经验性判断说成确定事实，也无法沉淀组织经验。

本项目的目标是做一个“安防设备诊断 Harness”，把 LLM 放进受控的工程框架中：

```text
LLM 负责推理
Harness 负责事实、权限、证据、状态、人工确认和评测
```

## 2. 项目一句话定位

> 面向安防设备运维的可信诊断 Agent Harness：通过只读设备工具、Evidence、Citation Policy、人工确认和质量评测，约束 LLM 基于可追踪事实完成故障诊断。

## 3. 与应用日志诊断项目的关系

本项目参考 `application-diagnosis-platform` 的工程经验，但不继承它的业务主线。

| 维度 | 旧项目 | 新项目 |
|---|---|---|
| 主诊断对象 | 应用服务异常 | 安防设备故障 |
| 主要事实来源 | 服务日志、源码、服务拓扑 | 设备状态、告警事件、配置快照、SOP |
| 典型案例 | NPE、连接拒绝、超时、连接池耗尽 | 摄像头黑屏、录像缺失、门禁刷卡失败、报警误报 |
| 核心复用 | Agent Harness 思想 | 重新实现为安防域 Harness |
| 不复用内容 | Java Lab、服务日志主线、源码诊断主线 | 不迁移 |

## 4. 总体架构

架构分为六层：

1. API 接入层：创建诊断、查询诊断、人工反馈、报告查询。
2. 应用编排层：控制一次诊断用例的事务边界、状态推进和 Agent 调用。
3. 领域层：安防设备、故障类型、证据、结论、人工确认和知识候选。
4. Agent Harness：Tool Registry、Strategy、Budget Guard、Citation Policy、Failure Guard。
5. Ports：LLM、DeviceGateway、Knowledge、Evidence、Audit、Evaluation。
6. Adapters：Static JSON、SQLite、Fake LLM、OpenAI-compatible LLM。

核心图见：[安防设备诊断 Harness 总览](../01-architecture/security-device-diagnosis-harness-overview.md)。

## 5. Phase 0 最小范围

Phase 0 只验证一个问题：

> 在不接真实设备、不调用真实模型的前提下，能否跑通摄像头黑屏诊断的最小可信闭环？

Phase 0 包含：

- `SecurityDiagnosisCase`
- `SecurityFaultType`
- `DeviceSnapshot`
- `DeviceAlarmEvent`
- `DeviceConfigSnapshot`
- `DiagnosisEvidence`
- `Tool Registry`
- `StaticDeviceGateway`
- `Fake LLM`
- 摄像头黑屏 demo

Phase 0 不包含：

- 真实设备网关；
- 真实视频流拉取；
- 设备重启或配置下发；
- LangGraph 多 Agent；
- 模型微调；
- Milvus / Elasticsearch；
- 企业权限系统；
- 工单系统。

## 6. 面试表达

可以这样讲：

> 我之前做过一个应用故障诊断 Agent，用来验证 Evidence、Tool Registry、Citation Policy、人工确认和评测这些 Agent 工程化能力。后来我发现单纯应用日志诊断和我的安防行业背景结合不够强，所以我新开了一个安防设备诊断 Harness 项目。新项目不再围绕 Java 服务日志，而是围绕设备状态、告警事件、配置快照和知识库 SOP 做诊断。两者关系不是复制，而是工程方法复用、业务领域重建。

## 7. 不能误解什么

- 这不是把旧项目改名换皮；
- 这不是完整企业级安防 AIOps 平台；
- 这不是自动修复设备故障系统；
- 这不是让 LLM 自由调用设备 API；
- Phase 0 只做只读诊断，不做写操作；
- confirmed 结论必须来自人工确认，不能由模型直接产生。
