# 从 0 到 1 构建可信诊断 Agent：我的成长、方法与反思

## 1. 这份文档记录什么

这不是 Phase 0～11 的功能清单，也不是把 Git 提交换一种方式抄一遍。它记录的是：

- 我最初如何理解问题，后来为什么改变理解；
- 一个能演示的 AI Demo，如何逐步变成一个有边界、可验证、可审计的工程；
- 我怎样设计领域、架构、开发流程和验收门禁；
- 哪些问题曾经通过了测试，却仍然在严格审计或真实链路中暴露；
- 我怎样判断下一步应该增加能力、补证据，还是停止功能堆砌；
- 如果重新从零开始，我会怎样用更短的路径得到更可靠的结果。

它和[Codex 与 CodeBuddy 协作编排器设计与学习手册](./Codex与CodeBuddy协作编排器设计与学习手册.md)
放在一起：本文讲“项目怎样成长”，后者讲“多 Agent 怎样接力，以及什么时候不该接力”。

## 2. 起点：我真正要解决的不是“让模型会诊断”

项目最容易走向的方案，是把日志、设备描述或告警丢给大模型，让模型返回一个看起来
专业的答案。这个方案很容易做出演示，但有五个无法回避的问题：

1. 模型依据了什么事实？
2. 它有没有调用错误的工具、使用错误的参数？
3. 工具失败时，它是否把猜测写成了事实？
4. 为什么这次修改比上个版本更好？
5. 如果结论造成误操作，谁拥有最终责任？

因此我逐渐把项目的中心从“LLM 诊断能力”改成了“可信诊断 Harness”：

> LLM 负责在受限事实内推理；确定性工程层负责权限、预算、状态、证据、引用、人工确认和评测。

这次定位变化是整个项目最重要的成长。它决定了后面所有架构选择，也让项目摆脱了
“只是套一个模型 API”的叙事。

## 3. Phase 0～11：能力不是堆出来的，而是一层层被证明的

| 阶段 | 当时面对的问题 | 建立的能力 | 我获得的认知 |
|---|---|---|---|
| Phase 0 | 怎样让模型不能随意行动 | 领域状态机、只读工具、Registry、Runner、Evidence、CitationPolicy、HumanReview | 先设计约束，再接模型 |
| Phase 1 | “摄像头黑屏”太宽泛 | 设备、通道、码流、平台拉流的多事实诊断与固定案例 | 业务诊断必须拆成可观察事实 |
| Phase 2 | 新故障域能否复用架构 | 录像计划、存储、回放事实和录像缺失规则 | 扩展领域，不复制 Harness |
| Phase 3 | 敏感身份数据怎样进入诊断 | 门禁事实、脱敏、候选规则与固定评测 | 事实可用不代表原始标识可见 |
| Phase 4 | “未发现目标”是否等于目标不存在 | 报警规则、复核事实、报告和评测 | unknown、false、missing 必须区分 |
| Phase 5 | 人工确认的经验怎样复用 | KnowledgeCandidate、状态治理、BGE Port、关键词/向量/混合检索 | RAG 的核心是知识治理，不是向量库名称 |
| Phase 6 | 进程重启、并发和数据损坏怎么办 | SQLite、迁移、深层脱敏、异常映射、乐观锁、审计、扫描、备份恢复 | 持久化不是“把 dict 换成数据库” |
| Phase 7 | 怎样证明版本真的变好 | Dev/Validation/Test、Code Grader、真实模型低频基线、发布门禁 | 评测必须参与设计，而非最后补测试 |
| Phase 8 | 标准答案本身可靠吗 | 双人盲标、裁决、失败归因、趋势、不可变数据集发布 | 评测数据也需要治理和审计 |
| Phase 9 | 怎样从静态样例走向设备接入 | 资产目录、能力模型、Adapter Registry、HTTP 契约、路由、受控降级、可观测指标 | Adapter 是事实边界，不是 SDK 包装器 |
| Phase 10 | 怎样安全地准备真实接入 | 历史基线、发布 Gate、授权清单、调用预算、dry-run Runbook | “技术可调用”不等于“已经获得授权” |
| Phase 11 | 模拟链路能否稳定复现真实协议问题 | ONVIF Adapter、RTSP、Toxiproxy、跨来源 Agent Loop、十轮门禁 | Simulator 是真机前的工程证明，但不是真机证明 |

### 3.1 第一阶段：先把模型关进边界里（Phase 0）

最初建立的不是复杂 Agent，而是一组不可绕过的不变量：

- 工具必须通过 Registry；
- 所有工具默认只读，并声明权限与风险；
- 工具失败不产生 Evidence；
- 结论至少引用一条当前诊断的 Evidence；
- `probable` 必须由多类设备事实支撑；
- 模型不能产生 `confirmed`；
- `confirmed` 只能来自满足状态条件的 HumanReview；
- Runner 有轮次和工具调用预算。

这里的关键经验是：状态机、权限、引用和预算不能写在 Prompt 里当作“希望模型遵守的
建议”，而要写成代码能够拒绝的规则。

### 3.2 第二阶段：从一个场景证明领域扩展方法（Phase 1～4）

我没有一开始同时开发四个故障域，而是先用摄像头黑屏跑通完整模板：

```text
业务现象
  → 可观察事实模型
  → DeviceGateway Port
  → 只读 Adapter / 样例
  → Tool Registry
  → Evidence
  → 候选规则
  → CitationPolicy
  → 报告
  → 固定案例评测
```

录像缺失、门禁异常和报警误报都复用了同一 Harness，只增加各自的领域事实、工具和规则。
这证明架构真正可扩展的标准不是“有很多抽象类”，而是新增业务域时不需要复制状态机、
Runner、权限、证据、人工确认和评测机制。

这个阶段还让我学会了三种非常重要的业务语义：

- `unknown` 不等于 `false`；
- “没有采集到”不等于“确定不存在”；
- 候选根因不等于人工确认的最终结论。

### 3.3 第三阶段：从诊断结果走向知识与数据可靠性（Phase 5～6）

继续增加第五个故障域的边际价值已经很低。因此 Phase 5 转向知识闭环：只有人工确认的
诊断才能生成 KnowledgeCandidate，候选知识还要经过状态治理，只有 confirmed 知识才能
被检索。BGE 被设计成独立服务，通过 EmbeddingPort 接入；项目可以比较 Keyword、Vector
和 Hybrid，而不会把领域层绑定到某个模型或 HTTP 服务。

Phase 6 把系统从进程内 Demo 推向可恢复工程：

- Repository 使用 Port，SQLite 只是 Adapter；
- Schema 变更必须经过 Alembic，不能用 `create_all` 冒充迁移；
- ORM 不进入 Domain，Session 不泄漏给 Application；
- 数据库异常映射为稳定应用异常，并在失败时 rollback；
- 聚合使用 version + CAS 检测陈旧更新，不自动重试业务动作；
- 审计事件追加写，一致性扫描只读，备份恢复是显式运维动作。

这里最深的认识是：可靠性不是一个“数据库已接入”的复选框，而是重启、迁移、并发、
异常、脱敏、备份和恢复共同构成的行为契约。

### 3.4 第四阶段：让评测决定能否发布（Phase 7～8）

固定测试只能证明代码符合已知断言，不能单独证明 Agent 质量。因此项目建立了：

- Dev Set：日常快速开发和失败复现；
- Validation Set：策略、Prompt、模型或配置的版本比较；
- Test Set：未见案例上的最终确认；
- Code-based Grader：格式、标签、工具、Evidence、泄漏等确定性指标；
- Model-based Grader：只用于难以程序化的语义质量，并保持低频；
- Human Grader：处理争议标签并承担最终裁决；
- 发布 Gate：P0、安全退化、指标退化和血缘不一致时阻塞。

真实模型第一次只有 0.5 标签准确率，后来又因输出结构失败得到 0。项目没有修改标准答案
迎合模型，而是向模型提供完整候选标签和合法 Evidence 类型，使用严格结构化输出，将标签、
工具和 Evidence 分开评分。最终复验达到标签 1.0、Evidence 合规 1.0，但工具 precision
仍为 0.75。这个结果比“全部满分”更有价值，因为它保留了下一步优化的真实方向。

Phase 8 又反过来审计评测本身：双人盲标、独立裁决、近重复检查、来源授权、版本不可变、
失败目录和趋势可比性。至此我理解到：如果标准答案、数据来源和版本血缘不可信，再漂亮的
评测分数也没有意义。

### 3.5 第五阶段：从模拟事实走到协议与设备边界（Phase 9～11）

真实设备接入不是把 SDK 调通就结束。Phase 9 先建立供应商无关的资产、能力、连接引用、
请求上下文和稳定错误分类，再用 Simulator 和本机 HTTP 契约验证：

- 资产不存在、禁用或缺能力时受控拒绝；
- Adapter 未就绪、超时、限流和部分事实时稳定降级；
- 失败调用不生成 Evidence；
- Simulator 报告固定标记为 `simulator_e2e`，不能冒充真机结果。

Phase 10 在技术入口前增加授权协议、预算和 dry-run。Phase 11 才正式接入只读 ONVIF、
RTSP 和 Toxiproxy，并把 ONVIF 设备事实、平台拉流事实、网络故障和视频内容事实汇入完整
Agent Loop。最终连续十轮实现基础场景 80/80、Agent Loop 40/40。

这条路径让我学会：越接近真实世界，越需要把“我们验证了什么”和“我们还没有证明什么”
写清楚。十轮 Simulator 稳定不等于真实设备兼容，更不等于公司生产上线。

## 4. 我形成的架构设计方法

### 4.1 先写不变量，再画组件

设计架构前先回答以下问题：

1. 哪些事实可以被信任，事实来自哪里？
2. 哪些状态转换绝不能由模型完成？
3. 哪些操作具有外部副作用？
4. 失败时必须保留什么，绝不能伪造什么？
5. 哪些数据不能进入日志、Evidence、报告和 Git？

只有回答这些问题后，才决定 Domain、Port、Adapter、Application 和 API 的边界。这样得到的
抽象服务于风险，而不是为了使用设计模式。

### 4.2 用六层职责隔离变化

| 层 | 负责什么 | 不应该负责什么 |
|---|---|---|
| Domain | 业务事实、状态机、不变量、脱敏 | HTTP、ORM、模型 SDK |
| Port | 稳定能力契约 | 厂商细节、重试策略 |
| Adapter | 协议、数据转换、错误分类 | 候选根因、状态推进 |
| Tool/Registry | 参数、权限、风险、调用门禁 | 直接确认结论 |
| Application | 编排、Evidence 落地、Citation、状态流转 | 解析底层协议 |
| Evaluation/Operations | 数据集、Grader、Gate、审计、恢复 | 改写业务真相迎合模型 |

判断边界是否合理，可以使用一个简单问题：如果把 ONVIF 换成另一家厂商 SDK，哪些文件
必须修改？答案应该主要集中在 Adapter 和装配层，而不是 Domain、规则和状态机。

### 4.3 确定性层掌权，模型层提议

模型可以：

- 选择允许的只读工具；
- 根据已采集 Evidence 组织候选解释；
- 提出排查顺序和下一步建议。

模型不可以：

- 绕过 Registry 调工具；
- 增加预算、权限或支持的设备能力；
- 把工具失败补成事实；
- 产生 confirmed；
- 自动重放 Agent 或人工审核动作；
- 修改评测标准答案让自己通过。

这不是削弱 Agent，而是把不确定性放在允许不确定的区域内。

### 4.4 Evidence 是系统的主干数据结构

一次诊断的价值不只在最终标签，而在这条可追踪链：

```text
设备/平台事实
  → ToolExecutionResult
  → EvidenceDraft
  → DiagnosisEvidence（ID + hash + source + reliability）
  → DiagnosisConclusion.cited_evidence_ids
  → HumanReview
  → KnowledgeCandidate
  → 后续检索与评测
```

当所有能力围绕 Evidence 连接时，报告、审计、知识沉淀、评测和真机联调可以共享同一套
可信基础；如果只有最终自然语言答案，这些能力都只能重新猜测模型当时做了什么。

## 5. 我形成的开发方法

### 5.1 每个 Phase 先写四件事

1. 阶段目标：本阶段只证明一个主要命题；
2. 允许修改：明确模块和新文件范围；
3. 禁止事项：真实外部访问、写操作、自动确认、越权依赖等；
4. 验收标准：成功、失败、安全、回归和残留检查。

一个 Phase 如果不能用一句话说清“完成后比之前多证明了什么”，说明范围太大或目标混乱。

### 5.2 使用纵向最小闭环，而不是横向铺骨架

优先跑通一个案例的完整路径，再批量扩展：

```text
一个领域对象
  → 一个 Adapter 行为
  → 一个只读工具
  → 一条 Evidence
  → 一个候选规则
  → 一份报告
  → 一个固定评测
```

这样可以尽早暴露层间契约问题，也避免一次创建大量尚未被真实调用的抽象。

### 5.3 红测试不仅覆盖成功路径

每项能力至少应覆盖：

- 正常路径；
- 边界值；
- 非法输入；
- 下游超时/不可用/错误响应；
- 状态不允许；
- 跨诊断或跨故障域引用；
- 敏感信息泄漏；
- 失败后的状态、数据和资源残留。

测试名称应表达业务不变量，例如“陈旧副本不能覆盖赢家”，而不是只写“update failed”。

### 5.4 对外部世界使用 Port，对测试使用确定性替身

FakeLLM、StaticDeviceGateway、Simulator、MockTransport 和本机契约服务并不是低质量替代品，
而是为了把变量固定下来。只有确定性基线稳定后，才低频调用真实模型、BGE 或授权设备。

但是替身的报告类型必须明确：`fake`、`simulator_e2e`、`real_model`、
`authorized_device_e2e` 不能混合统计或互相冒充。

## 6. 我形成的验收方法

### 6.1 五层验收金字塔

| 层次 | 主要回答的问题 |
|---|---|
| 单元测试 | 单个模型、规则、映射和异常是否符合契约 |
| 集成测试 | Port、Adapter、Repository、迁移是否正确协作 |
| 完整闭环 | Runner→Tool→Gateway→Evidence→Citation→Review 是否真实贯通 |
| 固定评测 | 多案例上的标签、工具、引用、安全与成本是否可比较 |
| 稳定/外部验收 | 多轮是否无随机失败；真实模型或真机差异是否受控 |

只跑新增测试不能证明没有回归；只跑全量测试也不能证明外部服务、进程生命周期和故障注入
正确。因此不同层次必须互补。

### 6.2 每次验收都要保留反证

一份可信验收至少说明：

- 实际运行了什么命令；
- 总数、通过数和失败数；
- 是否访问外部网络、模型、BGE 或设备；
- 是否生成临时凭证、数据库或运行文件；
- 停止后是否有进程、容器、toxic 或文件残留；
- 哪些事项明确没有验证。

“测试通过”只是证据之一，不是完整结论。

### 6.3 评测指标必须拆开

不能用一个总分掩盖问题。至少分别观察：

- 候选标签准确率；
- 工作流完成率；
- 工具 precision / recall；
- Evidence 合规率 / recall；
- 引用归属与多事实满足率；
- 敏感泄漏数；
- 超时、调用次数和成本；
- 争议案例数量。

这样才能判断问题发生在模型推理、工具选择、事实采集、引用修复还是评测标签。

## 7. 严格审计教会我的事

### 7.1 通过很多测试，仍然可能存在 P0

项目中真正有价值的修复包括：

- Evidence 去重时返回了新对象，导致后续引用一个并未挂接的 ID；
- `possible` 曾允许零引用，形成无证据结论；
- probable 引用补齐先去重再切片，知识 Evidence 挤掉了设备事实；
- Playback 的 `available/missing` 与 `file_count` 可能自相矛盾；
- 存储容量规则只看绝对容量，漏掉只有 `used_percent` 的设备；
- 构造后修改嵌套对象可能绕过脱敏，并让 Evidence hash 与落库内容不一致；
- ORM execute/commit/read 异常曾可能泄漏，rollback 与应用异常映射不完整；
- Runtime 曾允许故障域与工具能力不匹配，摄像头 Runtime 可以接受录像诊断；
- 无 version 的更新会丢失并发修改；有 CAS 后仍需证明冲突不自动重放 Agent 或 HumanReview；
- Device Lab 曾记录包装进程 PID，停止后遗留真正的 Python 子进程；
- 兼容清理曾只按命令行文本匹配，可能误杀提到脚本名的 PowerShell 宿主；
- 黑视频只有首个关键帧，客户端中途加入时出现随机解码失败。

这些问题共同说明：测试数量不是质量本身。质量来自测试是否覆盖真实不变量、反例、生命周期
和失败后的系统状态。

### 7.2 修复缺陷时不能只补当前例子

一次高质量修复应回答：

1. 根因在哪一层？
2. 是否还有其他入口能绕过修复？
3. 修复会不会改变已有业务语义？
4. 能否写一个失败前必红、修复后必绿的回归测试？
5. 是否需要真实探针而不只是 Mock？
6. 文档和验收口径是否同步？

例如深层脱敏没有在数据库 Adapter 再复制一套正则，而是重建安全 Domain 副本，复用唯一
脱敏规则并重算 hash。这样解决的是一类问题，而不是一个字段。

## 8. 我怎样避免项目偏离主干

### 8.1 为项目写一句不可轻易改变的主线

> 这是安防设备可信诊断 Harness：多来源事实由确定性工程层治理，LLM 只生成有证据的候选结论。

任何新需求都要回答它是否增强这句话。如果只是增加技术名词、故障域数量或模型自由度，
却没有增强事实可信、约束、评测或真实接入，就不应进入主线。

### 8.2 使用“主线检查卡”

开始一个阶段前检查：

- 它解决的是用户/运维人员的真实问题，还是简历关键词焦虑？
- 它新增的是必要能力，还是重复已有 Harness？
- 它能被确定性验收吗？
- 它是否放松 confirmed、Citation、权限或外部访问边界？
- 它会不会把 Simulator、Fake 或固定规则包装成生产事实？
- 完成后哪些事情仍然不能声称？

只要最后一项写不出来，就很容易过度包装。

### 8.3 对范围使用三张清单

每个 Phase 同时维护：

- 必须完成：构成最小闭环的内容；
- 可以完成：不改变主目标的增强；
- 明确不做：下一阶段、需要授权或高风险的事项。

“明确不做”不是偷懒，而是保护架构主干和验收因果关系。

### 8.4 设置停止规则

项目不应无限增加 Phase。满足以下条件后应封版：

- 核心业务闭环可重复；
- 安全与人工确认边界稳定；
- 数据可恢复、并发冲突可检测；
- 评测能够阻止退化；
- Simulator 多轮稳定；
- 至少一次受控真机试接入完成；
- 主要 P0/P1 已关闭。

Phase 11D 后停止新增故障域，转向文档、演示、教学和面试，是成熟度提升，而不是项目停止成长。

## 9. Codex 与 CodeBuddy 协作带来的额外成长

最初设想是 Codex 设计和审核、CodeBuddy 实现，从而减少 Codex 消耗并允许无人值守推进。
实验最终得到一个更克制的结论：可靠接力可以实现，但双 Agent 不一定更经济。

### 9.1 真正有效的机制

- worktree 隔离，避免两个 Agent 抢同一目录；
- Git commit 作为事实总线；
- 状态文件和进程退出事件替代模型轮询；
- HANDOFF、HOST_VALIDATION、REVIEW_RESULT 绑定 base/head；
- Max Turns 只允许原 worktree 续作一次；
- 审核使用新会话，不携带轮询历史；
- 宿主只执行事先批准的验收命令；
- 超出返修预算后明确转入 Codex/人工接管。

### 9.2 失败实验带来的结论

- 小任务的规格、交接和审核成本可能大于实现成本；
- 高耦合、安全、架构任务需要大量上下文，委派后返修成本高；
- 重复测试、批量文档、边界明确的中型机械实现更适合委派；
- “两个模型都工作了”不是收益，`cost per success` 才是；
- 没有成功任务，就只能记录 cost per attempt，不能宣称节省。

因此最终路由是：小任务和高风险任务由 Codex 直接完成；需求稳定、验收确定、实现量明显
大于审核量的中型任务才交给 CodeBuddy。这个结论本身就是一次重要的工程决策，而不是
自动化失败。

## 10. 如果让我重新做一次，我会怎样缩短路径

### 10.1 第一周：建立最小可信闭环

只做一个摄像头案例，完成 Domain、Port、只读 Tool、Evidence、Citation、Review 和五个固定
子案例。先证明约束和评测，不接数据库、不接 RAG、不接真实模型。

### 10.2 第二周：证明可扩展和可恢复

只增加一个差异明显的业务域，验证 Harness 复用；随后接 Repository、迁移、深层脱敏、
异常映射和重启恢复。优先审计失败路径，不追求测试数量。

### 10.3 第三周：建立质量闭环

划分数据集、拆分指标、保存 Baseline 血缘、建立发布 Gate。真实模型只跑少量 Validation，
不修改标准答案迎合输出。

### 10.4 第四周：协议模拟与真机试接入

先 Simulator + 本机契约 + 故障注入，再接正式只读 Adapter，完成十轮稳定后才申请一次真机
授权验证。真机完成后封版，不继续用新功能掩盖已有证明不足。

## 11. 我最终获得的能力

### 11.1 业务能力

- 把“黑屏、录像缺失、刷卡失败、报警误报”翻译为可观察事实；
- 区分设备事实、平台事实、内容事实、知识建议和人工结论；
- 理解运维诊断中的 unknown、部分事实、证据冲突和排查顺序。

### 11.2 架构能力

- 用 Domain/Port/Adapter 隔离业务和基础设施；
- 用状态机、权限、预算和 CitationPolicy 约束 Agent；
- 设计可插拔设备接入、知识检索、持久化和评测体系；
- 把外部服务失败映射为稳定、低泄漏的领域错误。

### 11.3 工程质量能力

- 使用固定案例、分层测试、真实探针和多轮稳定门禁；
- 处理迁移、rollback、CAS、审计、备份恢复和资源生命周期；
- 从反例出发设计脱敏、hash、并发和故障注入测试；
- 用报告类型和明确边界避免夸大验证结果。

### 11.4 Agent 工程能力

- 评估工具调用、工作流、Evidence 和标签，而非只看最终文本；
- 使用 Dev/Validation/Test 和多种 Grader 驱动迭代；
- 识别哪些决策必须确定性执行，哪些可以留给模型；
- 根据任务经济性选择单 Agent、双 Agent 或人工介入。

## 12. 我应该如何讲述这段经历

不要从“项目有 11 个 Phase、1633 个测试”开始。更有价值的表达是：

> 我最初也担心设备诊断只是把信息丢给大模型。于是我把问题改写为：怎样证明模型只能在
> 授权的只读事实内推理，而且每个结论都能追踪、复核和回归。围绕这个问题，我逐步建立了
> 领域状态机、工具权限、Evidence/Citation、人工确认、知识治理、持久化可靠性、评测发布
> Gate 和设备 Adapter。过程中严格审计暴露了引用补齐、深层脱敏、并发覆盖和进程残留等
> 问题，我没有用更多 Prompt 掩盖，而是把它们修成确定性不变量。最终系统在 Device Lab
> 完成十轮 80/80 场景和 40/40 Agent Loop 验证，下一步只剩授权真机只读试接入。

数字是证明，架构是手段，真正应该讲出来的是：我如何识别不可信、把风险变成约束、把约束
变成测试，再让评测决定系统能否继续演进。

## 13. 封版后的学习路线

真机验收完成后，我需要从“开发者”切换为“能解释设计的人”：

1. 不看代码画出业务链路和六层架构；
2. 用一个黑屏案例讲清事实采集、工具调用、Evidence、Citation 和 HumanReview；
3. 解释三次最有价值的缺陷及为什么原测试没发现；
4. 说明 Simulator、真实模型、真机和生产上线各自证明了什么；
5. 回答为什么不用自由 Agent、为什么不自动重试、为什么需要人工确认；
6. 现场运行一条固定 Demo，并能解释每一段输出；
7. 接受面试官基于回答继续追问，而不是背固定问答。

完成这些训练后，这个项目带来的成长才真正闭环：不仅“代码做出来了”，而且我能解释
为什么这样做、怎样证明它可靠、哪里仍有限制，以及下一次怎样做得更快。
