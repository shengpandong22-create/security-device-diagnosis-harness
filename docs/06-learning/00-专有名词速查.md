# 00｜专有名词速查

这份文档不重复讲链路，只做一件事：**把 01–06 里出现的专有名词一次说清。**

大多数读不懂源码的情况，不是因为逻辑复杂，而是因为同一个词在四层里承担不同职责
（例如 `Registry` 有工具注册表和设备适配器注册表两个）、或者一个词在两种状态下语义不同
（例如 `confirmed` 既是诊断状态也是知识状态）。遇到读不通的地方，先回这里查词，再回对应链路。

## 怎么用

- 第一遍：只看第 1、2 节，建立"谁负责什么"的整体印象。
- 读链路卡住时：查第 3–8 节对应分类。
- 面试前：重点看第 9 节「最容易搞错的 12 组」，那是被追问的高发区。

术语表里的「链路」列指向深入讲解的那一篇。

---

## 1. 一张分层全景图

```text
API 路由层 ──────────── HTTP 入参、身份角色、DTO、状态码映射
   │
Application Service ── 用例所有者：事务边界、状态推进、Evidence 落地、CAS 更新
   │
Domain ─────────────── 聚合、状态机、不变量、CitationPolicy（不依赖框架）
   │
Agent（Runner） ────── 受预算约束的"模型 ↔ 工具"循环，不触碰业务状态
   │
ToolRegistry ───────── 工具的白名单、权限、参数、只读、受控失败
   │
Tool ───────────────── 业务动作（如"查设备码流"），产出 EvidenceDraft
   │
DeviceGateway ──────── 只读设备事实契约（Port）
   │
RoutedDeviceGateway ── 资产/能力/授权/就绪度预检与确定性路由
   │
Adapter Registry ───── adapter_key → 具体 Adapter 的映射与 ready 状态
   │
Adapter ────────────── ONVIF / HTTP / Simulator / Static，真正说协议的一层
   │
设备 / 平台
```

横向还有三条独立链路：**Repository（持久化）**、**Knowledge（治理与检索）**、**Evaluation（评测与门禁）**。

## 2. 分层与角色

### 2.1 请求链路核心角色

| 术语 | 一句话定义 | 负责 | 不负责 |
| --- | --- | --- | --- |
| **Application Service**<br>（应用服务） | 用例所有者，`SecurityDiagnosisApplicationService` | 创建聚合、调用 Runner、把 Draft 落成 Evidence、修正引用、调用 CitationPolicy、CAS 更新、推进状态机 | 推理、协议访问、证据内容判断 |
| **Runner**<br>（`ToolLoopRunner`） | 受预算约束的"模型 ↔ 工具"循环 | 组装受限上下文、调用 LLM、执行 allowlist 内工具、回收 observation、返回 `ToolLoopResult` | 修改 Case 状态、把 Draft 落成 Evidence、持久化 |
| **Registry**<br>（`ToolRegistry`） | 工具注册与受控执行的**唯一**入口 | 注册期拒绝非只读工具、执行期复查风险等级、权限与故障域校验、参数校验、异常转受控失败、边界重建结果 | 业务判断、设备访问 |
| **Tool**（`BaseTool`） | 一个业务动作，如"查询设备码流" | 参数模型校验、声明权限与风险级别、把 Gateway 返回值转成 `ToolEvidenceDraft` | 直接改 Case、持有设备 URL |
| **Port** | 领域/应用依赖的抽象契约，只有签名没有实现 | 定义边界 | 任何具体技术 |
| **Adapter** | Port 的具体实现 | 网络、协议、ORM、向量服务等真实技术细节 | 领域规则 |
| **Bootstrap / Container** | 装配层，把 Port 与 Adapter 组起来 | 决定用内存还是 SQLite、用 Fake 还是真实实现 | 业务逻辑 |

关键界面（面试常问）：

```text
LLM Loop ──Draft──> Application ──Policy/CAS──> Case / DB
```

Runner 返回草稿，Application 才落地。这是"推理"与"事务"的分界。

### 2.2 装配入口（三个名字容易混）

| 名称 | 位置 | 用途 | 副作用 |
| --- | --- | --- | --- |
| `create_app()` / 模块级 `api.app.app` | API 工厂 | 应用工厂与既有测试 | 无（内存装配） |
| `build_container()` / `build_phase1~4_container()` | `bootstrap/container.py` | 评测与 demo（内存 + FakeLLM） | 无 |
| `build_runtime_container()` | `bootstrap/container.py` | **正式本地运行**（SQLite） | 建目录 / 迁移 / 启服务 |
| `RuntimeContainer` | `runtime.py` | 独占 Engine 生命周期，`close()` 可重复调用 | — |

正式 Runtime 当前**只装配摄像头黑屏**一个故障域，见 [ADR-001](../01-architecture/ADR-001正式Runtime能力边界.md)。

### 2.3 设备接入角色（链路三详述）

| 术语 | 一句话定义 | 不负责 |
| --- | --- | --- |
| **AssetCatalog** | 资产目录：设备是谁、是否启用、声明了哪些能力 | 发网络请求 |
| **Adapter Registry** | `adapter_key` → Adapter 的确定性映射与 ready 状态 | 猜测设备能力 |
| **Router**（`RoutedDeviceGateway`） | 资产/能力/授权/就绪度预检与**确定性路由** | 伪造缺失事实、fallback |
| **Authorization**（`DeviceAuthorizationSession`） | 运行时授权与调用预算消费 | 保存明文凭证 |
| **ONVIF Adapter** | SOAP / HTTP Digest、响应解析、稳定错误分类 | 业务结论 |

> **Router 与 Registry 的区别（必背）**：Registry 解决"名字到实现的映射"；Router 解决"这个资产、这个能力、这个运行状态下该不该调用哪个实现"。分开后可以独立验证重复注册、未就绪、缺能力等错误。

## 3. 领域对象

| 术语 | 一句话定义 | 关键点 |
| --- | --- | --- |
| **Case**<br>`SecurityDiagnosisCase` | 一次诊断聚合，同时也是状态机与不变量载体 | 带 `version`；`status` 只能经领域方法变更 |
| **Evidence**<br>`DiagnosisEvidence` | 一条**已观察到的事实**，可被结论引用 | 构造期先脱敏再基于最终内容重算 `content_hash`；同诊断内按 hash 去重 |
| **EvidenceDraft**<br>`ToolEvidenceDraft` | 工具产出的证据**草稿**，还没有 `diagnosis_id` | 由 Application 落成真实 Evidence；失败结果必须为空 |
| **Conclusion**<br>`DiagnosisConclusion` | 模型/规则给出的**候选**结论 | `confidence` 只能是 `possible` / `probable` |
| **HumanReview** | 人工复核记录 | **唯一**能产生 `confirmed` 的动作来源 |
| **KnowledgeCandidate** | 可审核的知识单元，也是 RAG 的检索单元 | 7 个结构化字段，不是文本块 |
| **KnowledgeReview** | 对知识候选的人工审核记录 | 与 `HumanReview` 是两套不同对象 |

`Conclusion` 里两个引用字段必须分清：

| 字段 | 含义 |
| --- | --- |
| `model_cited_evidence_ids` | 模型**原始**给出的引用 |
| `cited_evidence_ids` | Harness 修正后**最终生效**的引用 |

配套标记：`citation_repaired`（引用被自动修正过）、`confidence_downgraded`（可信度被降级过）。
分开保存的原因是：不能让"Harness 修好了引用"被误解成"模型自己引用正确"。

## 4. 状态与枚举

### 4.1 诊断状态 `SecurityDiagnosisStatus`（链路一、二）

| 值 | 含义 |
| --- | --- |
| `created` | 已创建，尚未开始 |
| `investigating` | 正在推理与采集事实 |
| `waiting_for_input` | 缺信息，等待补充 |
| `waiting_for_confirmation` | 候选结论已通过 CitationPolicy，等待人工决定 |
| `confirmed` | **终态**，已由人工确认 |
| `rejected` | **终态**，已被人工作废 |
| `inconclusive` | **终态**，无法得出结论 |

三条硬约束：

1. `confirmed` **不在任何普通状态跳转的目标集合中**；
2. `confirmed` 只能由 `apply_human_review(CONFIRM)` 产生；
3. `confirmed`、`rejected`、`inconclusive` 是终态，不能再次变更。

### 4.2 候选可信度 `ConclusionConfidence`（链路二）

| 值 | 含义 | 门槛 |
| --- | --- | --- |
| `possible` | 依据较弱 | 至少一条引用；只引用知识 SOP 也只能停在这里 |
| `probable` | 机器候选的**最高**等级 | 至少引用 **2 类不同设备事实** Evidence，且不得依赖 `low` 可靠性设备证据 |
| ~~`confirmed`~~ | **不存在于该枚举** | 模型在类型层就无法表达 |

### 4.3 故障域 `SecurityFaultType`

`camera_black_screen` / `recording_missing` / `access_card_failed` / `alarm_false_positive`

其中**正式 Runtime 当前只开放 `camera_black_screen`**，其余三域为独立闭环与固定评测能力。

### 4.4 知识状态与来源（链路五）

| 枚举 | 值 |
| --- | --- |
| `KnowledgeCandidateStatus` | `candidate` / `confirmed` / `rejected` / `retired` |
| `KnowledgeCandidateSource` | `diagnosis_confirmation` / `manual_seed` / `imported` |
| `KnowledgeReviewAction` | `confirm` / `reject` / `retire` |

只有 `confirmed` 可被检索；`retired` 保留审计历史但退出召回（优于物理删除）。

### 4.5 人工审核动作 `HumanReviewAction`（链路二）

`confirm` → `confirmed`｜`reject` → `rejected`｜`request_more_info` → `waiting_for_input`

### 4.6 工具风险与权限（链路一）

| 枚举 | 值 |
| --- | --- |
| `ToolRiskLevel` | `READ_ONLY` / `MUTATING`（**只有 `READ_ONLY` 允许注册**，注册期与执行期各检查一次） |
| `ToolPermission` | `device:read` / `knowledge:read` |

### 4.7 设备能力与失败分类（链路三）

`DeviceCapability`：`status` / `channel` / `stream` / `alarm` / `config` / `recording` / `access` / `alarm_diagnosis`

**两套失败分类必须分清**（这是最容易答错的点之一）：

| 枚举 | 所在层 | 用途 |
| --- | --- | --- |
| `DeviceAdapterErrorKind` | **Adapter 层** | Adapter 内部抛出：`authentication` / `timeout` / `rate_limited` / `unavailable` / `unsupported_capability` / `invalid_response` |
| `DeviceFailureKind` | **工具层** | 对外稳定分类，供 LLM 与评测消费：`asset_not_found` / `asset_disabled` / `capability_missing` / `adapter_not_ready` / `authentication` / `timeout` / `rate_limited` / `unavailable` / `unsupported_capability` / `invalid_response` / `routing_context_required` / `unexpected` |

`classify_device_failure()` 负责把前者与各类受控异常统一映射为后者；**未识别异常一律归为 `unexpected`，绝不拼接 `str(exc)`**。

### 4.8 证据分类（链路一、三）

- `EvidenceType`：`device_status` / `device_alarm` / `device_config` / `device_channel` / `device_stream` / `platform_pull` / `recording_plan` / `storage_status` / `playback_check` / `access_controller` / `access_door` / `access_credential` / `access_policy` / `access_event` / `alarm_rule` / `alarm_signal` / `alarm_environment` / `alarm_verification` / `alarm_correlation` / **`knowledge_sop`** / **`human_feedback`**
- `EvidenceSource`：`device_gateway` / `knowledge_base` / `human`
- `Reliability`：`high` / `medium` / `low`

只有"设备事实类" EvidenceType 能支撑 `probable`；`knowledge_sop` 不属于设备事实。

## 5. 约束机制（这些名词背后都是一个闸门）

| 术语 | 一句话定义 | 代码位置 |
| --- | --- | --- |
| **CitationPolicy** | 结论引用的确定性门禁：归属、故障域、可信度合法性、至少一条引用、`probable` 设备事实数量与可靠性 | `domain/citation_policy.py` |
| **不变量**（invariant） | 无论用哪个 Runtime / LLM / 工具都必须成立的条件。例如 `conclusion.diagnosis_id == case.diagnosis_id` | `domain/case.py` |
| **allowlist / 白名单** | 两层含义：Runner 的 `tool_allowlist`（本次允许哪些工具）与授权清单的 `allowed_operations`（允许哪些只读操作） | `agent/runner.py`、`device_authorization.py` |
| **预算**（`ToolLoopBudget`） | Runner 的资源上限：`max_rounds=3`、`max_tool_calls=5`、`timeout_seconds=30`、`max_model_response_chars`、`max_observation_chars`、`max_context_chars` | `agent/runner.py` |
| **调用预算** | 授权层计数：`max_total_calls` + `max_calls_per_operation`；**deny 不消费预算，allow 时两个计数原子递增** | `device_authorization.py` |
| **CAS / 乐观锁** | Compare-And-Swap：`UPDATE ... WHERE id=? AND version=?`；`rowcount=0` 且 ID 存在则为冲突 | `adapters/persistence/` |
| **version** | 只代表**成功持久化次数**：新建为 0，首次 `save()` 后为 1，每次 `update()` 成功后 +1。普通领域状态变化**不会**自增 | `domain/case.py`、`domain/knowledge.py` |
| **ConcurrentUpdateError** | 陈旧副本试图覆盖较新状态时抛出，API 映射为 **409 `concurrent_update`**，**不自动重试** Agent 或 Review | `application/errors.py` |
| **脱敏**（redaction） | 凭证类字段统一替换为 `***REDACTED***`；`domain/redaction.py` 是**唯一**入口 | `domain/redaction.py` |
| **深层安全规范化** | 写入前对整个聚合重新 `model_validate`，让嵌套 validator 重跑，防御"构造后被就地修改"绕过 | `domain/aggregate_sanitization.py`、`adapters/persistence/mapping.py` |
| **追加式审计**（append-only audit） | 审计事件只能追加，不可被当普通聚合覆盖 | `adapters/persistence/audited_write.py` |
| **一致性扫描** | **只读**检查 Review / Evidence / Audit 的归属与结构；扫描与修复分离 | `application/consistency.py` |
| **受控失败 / 受控降级** | 失败一律转成稳定分类 + 安全文案，**不携带 EvidenceDraft**，不泄漏底层异常 | `tools/device_failures.py`、`tools/registry.py` |
| **fail-closed / 默认拒绝** | 拿不到授权清单就拒绝（`missing_manifest`）；拿不到事实就不产生 Evidence | `device_authorization.py` |
| **半开区间** | 授权时间窗语义为 `valid_from <= now < valid_until` | `device_authorization.py` |
| **report_kind / provenance** | 报告必须携带结果来源，区分 Static/Fake、Simulator、真实模型、授权真机 | `evaluation/` |

## 6. 设备接入链路（链路三）

| 术语 | 一句话定义 |
| --- | --- |
| **DeviceGateway** | 只读设备事实的 Port，共 19 个只读方法；**接口内不存在任何写方法** |
| **`adapter_key`** | 资产指向 Adapter 的键。**不出现在工具参数中**，因此模型无法选择路由 |
| **Asset / `DeviceAsset`** | 非敏感设备描述：`device_id` / `device_type` / `adapter_key` / `capabilities` / `enabled` |
| **Connection Profile** | 非敏感连接引用：`protocol` / `endpoint_alias` / `credential_reference`；禁止 URL、userinfo 与明文凭证 |
| **AuthorizationManifest** | 不可变的**授权声明**：环境别名、资产范围、凭证引用、时间窗、只读操作集、总预算、单操作预算 |
| **DeviceAuthorizationSession** | 运行时**消费记录**：锁内完成预检与预算替换；`rotate()` 是唯一预算重置入口；`close()` 后稳定返回 `session_closed` |
| **`AuthorizationDenyReason`** | 稳定拒绝原因码：`missing_manifest` / `environment_mismatch` / `not_yet_valid` / `expired` / `asset_out_of_scope` / `operation_not_allowed` / `total_budget_exhausted` / `operation_budget_exhausted` / `session_closed` / `invalid_asset_alias` |
| **业务操作预算 vs 网络交换预算** | Digest 的 challenge-response 可能包含两次网络交换，所以"一个业务操作"不等于"一个网络包"。契约必须写明计量单位 |
| **Simulator** | 高保真虚拟设备，用于确定性回归与故障注入，**不是真机替代品** |
| **Toxiproxy / toxic** | 注入延迟、超时、连接重置等网络故障的开源工具 |
| **ONVIF** | 设备互操作协议；本项目只做严格只读用途 |
| **WS-Discovery** | 发现局域网内设备服务 |
| **WS-Security `PasswordDigest`** | ONVIF 的一种认证方式（摘要而非明文密码） |
| **HTTP Digest / RTSP Digest** | 另一类摘要认证；`qop` 需要显式处理，安全边界仍不可省 |
| **SOAP** | ONVIF 的消息格式；解析必须受资源边界保护（禁止 DTD / 实体声明） |
| **Profiles / Stream URI / XAddr** | ONVIF 的媒体配置、取流地址与服务地址；均不得写入报告 |
| **RTSP OPTIONS** | 探活请求，用于验证流端点协议可达性；**不代表画面正常** |
| **ffmpeg `blackdetect`** | 抽帧检测持续纯黑的本地工具，用于"协议健康但画面纯黑"场景 |

## 7. 知识与检索（链路五）

| 术语 | 一句话定义 |
| --- | --- |
| **RAG** | 检索增强生成。本项目里它的角色是**提供历史经验与 SOP**，不提供现场设备事实 |
| **confirmed-only** | 只有人工确认过的知识才允许被召回；candidate / rejected / retired 一律隔离 |
| **反馈污染** | 若候选知识被召回，会形成"模型猜测 → 写入知识 → 引用自身猜测"的闭环 |
| **SOP** | 标准作业程序；本项目以 `knowledge_sop` 作为 EvidenceType，固定 `reliability=LOW` |
| **EmbeddingPort** | 向量化契约：`embed_query()` / `embed_documents()` |
| **FakeEmbeddingAdapter** | 确定性测试用向量实现；其指标**不能**冒充真实 BGE 指标 |
| **BGE** | `bge-small-zh-v1.5`，独立本机 HTTP 服务（`/v1/embeddings`，512 维）；主服务未启动时不得被隐式拉起 |
| **Keyword Retriever** | 中文词法检索：英文数字词项 + 中文**二元组**切分，有最小交集阈值 |
| **Vector / Semantic Retriever** | 纯向量检索，用于与 Keyword / Hybrid 做同变量对照 |
| **HybridKnowledgeRetriever** | 融合词法排名与语义排名 |
| **RRF** | Reciprocal Rank Fusion，按**排名**而非分数融合：`weight / (rrf_k + rank)`；本项目权重为词法 `1.2`、语义 `1.0`，`rrf_k=60` |
| **`min_semantic_score`** | 语义检索最低相似度阈值（本项目 `0.35`），低于阈值不进入候选 |
| **`keyword_fallback`** | Embedding 服务失败时的**显式**降级标记；不得把 keyword 结果冒充 hybrid |
| **Recall@K / MRR** | 检索评测指标；本项目的 12 条固定集只能建立回归基线 |
| **分块**（chunking） | 把长文档切成检索单元；本项目**未实现**——检索单元是结构化 `KnowledgeCandidate`，一条知识一个向量 |

> **本项目的检索单元是结构化对象，不是文本块。** 这一点决定了它与"文档问答型 RAG"在问题域上不同：通用 RAG 的核心难题是**结构丢失**，本项目是**结构可信**。

## 8. 评测与发布（链路六）

| 术语 | 一句话定义 |
| --- | --- |
| **Dataset / Registry** | 版本化评测数据集；入口 `evaluation/dataset.py` |
| **Dev / Validation / Test** | 三个划分：Dev 日常调优、Validation 版本比较、Test 保持未见性做最终确认。**Test 反复用于调参就不再是 Test** |
| **EvaluationOutput** | 评测输出，必须由 grader 从真实 Case / Evidence / Conclusion / Review / 工具轨迹**复算**，不能由执行者自报 |
| **Code Grader** | 确定性评分器；核心要求是**可复算** |
| **Failure Attribution** | 失败归因：模型输出 / 工具选择 / 设备事实 / 引用 / 工作流 / 基础设施 |
| **History** | 保存可比较的运行记录，支持趋势与基线对比 |
| **Baseline / Candidate** | 基线运行与候选运行；只有同数据集、模型、Prompt、配置、Runner、环境才可比较 |
| **Release Gate / GatePolicy** | 发布门禁：把回归阈值转成可执行的发布决定 |
| **macro-F1** | 宏平均 F1，必须从**逐案例混淆矩阵**复算，避免小类被淹没 |
| **tool precision / tool recall** | 调用的工具里有多少必要 / 应调的工具有没有漏 |
| **evidence compliance / evidence recall** | 引用是否合规 / 关键事实是否收集齐 |
| **workflow success** | 多步链路是否完成 |
| **human review rate** | 仍需人工争议处理的比例 |
| **Human Dispute Review** | 语义等价标签等分歧进入人工裁决，形成可审计结论 |
| **`publish_dataset_version()` / `verify_dataset_release()`** | 数据集发布与验证入口；`evaluation/release.py` |
| **`null` vs `0`** | `null` 表示**不可得**，`0` 表示**确实测得零**，两者不能混用 |

## 9. 最容易搞错的 12 组

### 1. `confirmed` 有三个不同语境

| 语境 | 含义 |
| --- | --- |
| `SecurityDiagnosisStatus.CONFIRMED` | 诊断终态，**只能由人工 review 产生** |
| `KnowledgeCandidateStatus.CONFIRMED` | 知识治理状态，**只能由知识审核产生** |
| `ConclusionConfidence` | **不存在这个值**，模型最高只能 `probable` |

### 2. Evidence vs EvidenceDraft

`Draft` 是工具产出、还没归属诊断；`Evidence` 是 Application 落地、有 `evidence_id` 与 `diagnosis_id`。**失败结果不带任何 Draft。**

### 3. Runner vs Application Service

Runner 是**推理循环**，Application Service 是**事务边界**。Runner 返回 `ToolLoopResult`，从不修改 Case。

### 4. Router vs Registry

Registry 管"名字到实现的映射"；Router 管"该不该用、用哪个"。合并会得到一个业务上帝类。

### 5. `waiting_for_confirmation` vs `confirmed`

前者是"候选已通过引用门禁，等人决定"；后者是"已有身份主体确认"。**前者不是后者的草稿态。**

### 6. `possible` vs `probable`

不是"低/高置信度"这么简单：`probable` 有**结构化门槛**（≥2 类设备事实 + 不得依赖低可靠证据），过不了就降级为 `possible`。

### 7. 业务操作预算 vs 网络交换预算

一次业务查询在 Digest 下可能是两次网络交换。**混算会让预算失真。**

### 8. `DeviceAdapterErrorKind` vs `DeviceFailureKind`

前者是 Adapter 内部错误分类，后者是对外稳定分类。面试时若混用，会暴露没读过代码。

### 9. 领域脱敏 vs 持久化深层规范化

Domain 构造期保证正常入口；Adapter 边界防御"构造后被就地修改"。**两者复用同一套规则，是纵深防御而非重复实现。**

### 10. 乐观锁 ≠ 完全并发安全

它只做冲突**检测**：不提供自动合并、串行化或分布式锁。冲突后必须由调用方重新读取再决策。

### 11. 固定评测 ≠ 生产准确率

如实测 2/2 只能说"在版本化 Validation Set 的两条受限案例上为 2/2"，并附模型、协议与调用边界。

### 12. Simulator vs 授权真机

Simulator 证明"故障映射、超时降级、循环稳定"；授权真机只证明"该设备上的指定只读协议闭环"。**两者不得混算，报告必须携带 `report_kind` / provenance。**

Application Service  管事务，不管推理

Router               管路由，不管协议

Repository           管保存，不管领域
