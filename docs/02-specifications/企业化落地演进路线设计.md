# 可信安防设备诊断 Agent 企业化落地演进路线设计

## 1. 目标

本文不是继续增加 Phase，而是回答：当前 Harness 距离企业落地还缺什么、为什么必须补、怎样按价值与风险逐步建设。

企业化完成的标志不是“部署成功”，而是：真实用户、租户、资产和责任主体进入链路；质量、安全、可靠性和成本都有
可复算证据；故障与回退经过演练；业务指标证明系统值得持续运营。

目标架构见：[可信安防诊断 Agent 企业化目标架构](../01-architecture/enterprise-evolution-target.md)。

## 2. 当前基线与差距

### 已具备

- LLM、只读 Tool、Evidence、CitationPolicy、HumanReview 的可信诊断链；
- 资产路由、授权预算、受控错误及 Simulator/Toxiproxy 故障注入；
- 四故障域固定回归、真实模型小规模评测；
- SQLite/Alembic、深层脱敏、CAS、审计、一致性扫描与备份恢复；
- KnowledgeCandidate 治理及 Keyword/BGE/Hybrid 检索；
- 一台授权 Wi-Fi 摄像头的 ONVIF/RTSP Digest 最小只读闭环。

### 企业化缺口

| 缺口 | 为什么必须补 | 不补的风险 |
| --- | --- | --- |
| 真实业务流程和用户 | 判断建议是否真正缩短处置时间 | 技术闭环没有业务价值 |
| 企业身份、RBAC、租户 | Review、资产、知识和审计需要真实责任主体 | 数据越权、责任不成立 |
| 多资产与连接治理 | 单设备不能代表资产群 | 容量、兼容性未知 |
| 生产数据面 | SQLite 只验证单机语义 | 多实例与恢复不可控 |
| Model Gateway | 模型有配额、漂移、成本和供应商故障 | 质量与费用不可治理 |
| 异步任务和人工队列 | 设备调用与复核跨越 HTTP 生命周期 | 任务丢失或重复执行 |
| 可观测和 SLO | 测试通过不等于长期稳定 | 线上问题无法定位 |
| 线上评测闭环 | 固定小样本不代表真实分布 | 门禁逐渐失真 |

## 3. 四条演进原则

1. **先证明业务闭环，再扩大技术规模。** 首个试点只选摄像头黑屏等高频、只读、可衡量场景。
2. **概率规划、确定执行、人工担责。** 企业化不放松 confirmed、Evidence、权限和审计边界。
3. **证据强度匹配结论强度。** Fake、Simulator、真实模型、授权设备和生产指标分开统计。
4. **模块化单体优先。** 只有独立扩缩容、团队所有权或故障隔离产生真实压力时才拆服务。

## 4. 目标能力设计

### 4.1 企业身份与租户

**为什么：** 当前 reviewer 是领域字段，企业需要证明谁代表哪个组织、以什么角色做出确认。

**如何拓展：**

- 接入 OIDC/OAuth2 SSO，API Gateway 验证身份；
- Case、Asset、Knowledge、Dataset、Audit 全部带 tenant_id；
- RBAC 至少区分 operator、reviewer、knowledge_reviewer、dataset_reviewer、admin；
- operator 与 reviewer 默认职责分离，高风险动作使用双人原则；
- 人类身份与 Service Account 分离，凭证进入 Secret Manager；
- 审计记录 actor、tenant、role、request_id 和 policy decision。

**验收：** 跨租户访问全部拒绝；operator 不能确认自己的结论；身份缺失不能匿名降级执行。

### 4.2 资产与设备 Connector 治理

**为什么：** 企业接入的是持续变化的资产群，不是手工输入地址的单设备脚本。

**如何拓展：**

- Asset Catalog 与 CMDB/设备平台同步厂商、型号、固件、站点、能力和 owner；
- Connector 插件声明 capabilities、读写风险、协议与兼容版本；
- 资产只保存 credential reference，运行时短期取密钥；
- 按 tenant/asset/operation 设置并发、速率、timeout、circuit breaker 和预算；
- 建立 Simulator 契约测试 → 实验室设备认证 → shadow → 正式准入的兼容矩阵；
- 写操作保持独立产品面，要求审批、幂等、回滚和强审计。

**验收：** 缺资产、禁用、缺能力、未就绪、认证失败、超时和限流均有独立错误与指标，绝不回退假数据。

### 4.3 生产数据面

**为什么：** 多实例、增长数据和恢复目标超出单机 SQLite 的适用范围。

**如何拓展：**

- PostgreSQL 保存 Case、Knowledge、版本和审计元数据，保留 Repository Port 与 CAS；
- 大对象进入受控 Object Store，只保存哈希、引用、租户、ACL 和保留期；
- Alembic 使用 expand/migrate/contract 支持滚动升级；
- 配置加密、PITR、RPO/RTO、备份恢复演练和数据删除策略；
- 使用 transactional outbox 连接工单/事件，避免数据库成功而消息丢失；
- 审计可增加 hash chain/WORM 归档，但不宣称绝对不可篡改。

**验收：** 双实例 CAS、故障切换、迁移兼容、备份恢复和租户隔离均有演练证据。

### 4.4 Model Gateway 与运行时治理

**为什么：** 真实模型存在供应商差异、429、漂移、费用和数据合规问题。

**如何拓展：**

- Model Gateway 统一协议，记录 model/prompt/tool-schema 版本；
- 按 tenant、fault_type、风险和成本路由模型；
- 配置 timeout、熔断、并发、token/费用预算与无自动无限重试；
- structured output 严格校验，模型不可用时显式降级到规则/人工；
- prompt、模型和工具 schema 变化必须经过 Validation、shadow 和 Release Gate；
- 仅记录脱敏 metadata 与 usage，原始内容按合规策略保存。

**验收：** 429、超时、非法 JSON、越权 ToolCall、预算耗尽和供应商不可用都有可归因降级。

### 4.5 异步工作流和人工队列

**为什么：** 设备请求、模型调用和人工复核不能长期占用同步 HTTP 请求。

**如何拓展：**

- API 创建 diagnosis command 并返回 ID，Worker 执行可恢复任务；
- 队列定义幂等键、租约、timeout、取消、死信和最大重试；
- Case 状态机仍是业务真相，队列状态不能替代领域状态；
- 人工队列支持指派、SLA、升级和补充信息；
- 工单集成使用 Outbox/Inbox 与 correlation_id，避免双写。

**验收：** Worker 崩溃、重复投递和超时不重复写 Evidence、不重放 Review、不丢审计。

### 4.6 知识与 RAG 治理

**为什么：** 企业知识持续变化，错误知识形成反馈污染比召回率低更危险。

**如何拓展：**

- 保持 candidate → confirmed/rejected/retired，增加 owner、适用固件、有效期和变更原因；
- 文档摄取增加解析质量、分块版本、ACL、PII 扫描和删除传播；
- Embedding 与索引版本化，重建采用双索引切换；
- 检索先 tenant/ACL/fault_type/status 过滤，再进行 Keyword/BGE/Hybrid 排名；
- 线上反馈只生成 candidate，不自动提升为 confirmed。

**验收：** 跨租户知识零召回；retired 立即退出；每条结果能追溯来源与治理记录。

### 4.7 可观测、SLO 与成本

**为什么：** 企业关心持续稳定和处理效率，不是单次 Demo 是否成功。

**如何拓展：**

- OpenTelemetry trace 串联 API、Agent round、Tool、Gateway、Model、Repository 和 Review；
- 指标覆盖成功率、P50/P95/P99、错误分类、轮次、工具数、模型调用、token/费用、人工复核率和降级率；
- 日志结构化、统一脱敏，带 tenant/request/diagnosis/tool_run 标识；
- 定义用户影响 SLO 与 error budget；
- 核心经营指标使用 cost per successful diagnosis、MTTR、一次解决率和人工分钟数。

**验收：** 任一失败能追到 trace、工具、Evidence、Review 与版本；不可得 token 保持 null；汇总可从明细复算。

### 4.8 评测与发布治理

**为什么：** 真实流量会变化，固定小数据集会逐渐失去代表性。

**如何拓展：**

- 数据集按故障域、厂商、固件、难度和来源分层，Dev/Validation/Test 权限隔离；
- 人工驳回、争议和失败 trace 经审核进入候选池；
- 离线 eval → 真实模型 → shadow → canary → 生产监控形成递进证据；
- Gate 同时看质量、安全、成本、延迟和关键切片，不只看总体准确率；
- 发布 manifest 绑定代码、模型、prompt、工具、数据集和 grader 版本；
- 模型、prompt、工具 schema 和应用都能独立回退。

**验收：** 任一发布决定可重建输入、指标、阈值、审批人与回退对象。

## 5. 分阶段落地路线

### Stage 0：企业试点准备（4～6 周）

范围：单租户、单故障域、10～50 台设备、模块化单体。

- 选定摄像头黑屏，建立人工处理基线与 KPI；
- 接 SSO、最小 RBAC、reviewer 职责分离；
- 正式 Runtime 切 PostgreSQL，完成迁移与恢复演练；
- 接一个资产源、一个真实设备平台/Connector；
- 上 OpenTelemetry、Model Gateway 和基础 SLO；
- 只做 shadow，不影响原工单与设备。

退出条件：连续两周数据完整；零越权写操作；诊断全链路可追踪；能与人工基线比较。

### Stage 1：受控生产试点（6～10 周）

范围：1～3 个站点、只读诊断、人工确认必选。

- 建立 Worker、人工队列和工单 Outbox；
- canary 限制租户、站点、设备、并发和模型预算；
- 每周审查误报、漏报、人工驳回、MTTR 和成本；
- 演练模型不可用、设备平台限流、数据库故障和版本回退。

退出条件：SLO 达标，无 P0 安全事件，业务 KPI 有证据改善，回退演练通过。

### Stage 2：多租户与规模化（由真实压力触发）

- tenant 全链路配额和数据隔离；
- Connector 认证计划与兼容矩阵；
- 水平扩容、队列分区与容量规划；
- 企业 Secret Manager、审计留存和合规删除；
- 只按独立扩缩容/故障隔离/团队所有权拆 Model、Connector 或 Evaluation Worker。

退出条件不是“上 Kubernetes”，而是容量、隔离和灾难恢复满足既定目标。

### Stage 3：有限自动处置（独立立项）

只读诊断稳定后才考虑低风险动作。每个动作必须有审批策略、幂等、dry-run、前置检查、回滚、执行后验证和 kill switch；
设备重启、配置修改等高风险动作默认仍需人工。

## 6. 企业试点验收指标

| 类型 | 指标 |
| --- | --- |
| 业务 | MTTA/MTTR、一次解决率、补充信息率、建议执行率、每次成功诊断人工分钟数 |
| 质量 | 标签、工具、Evidence 分项指标，人工接受/驳回/争议率 |
| 安全 | 越权工具、写操作、跨租户访问、敏感泄漏必须为零 |
| 可靠 | SLO、P95/P99、超时、熔断、降级、CAS 冲突、队列积压 |
| 成本 | 每次成功诊断的工具数、模型调用、token、费用和人工成本 |

所有指标必须带分母、时间窗、租户/场景切片和来源；不可得字段保持 null。

## 7. 最小部署拓扑

```text
Enterprise SSO / API Gateway
            │
  Diagnosis Application（2 实例）
       ├── Model Gateway ── Approved LLM
       ├── Task Queue ── Diagnosis Workers
       └── Connector Workers ── Device Platform / ONVIF
            │
  PostgreSQL + Object Store + Audit Archive
            │
  Observability Backend / Evaluation Pipeline
```

初期可以同进程部署多个模块。边界先在代码、权限、数据和指标上成立，再根据真实压力拆分。

## 8. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 同时接多厂商、多域、多模型 | 单场景试点与退出条件 |
| 模型越权或写设备 | 最小 allowlist、Policy、审批、kill switch |
| 错误知识反馈污染 | confirmed-only、双人治理、retired |
| 对固定数据集过拟合 | 隐藏 Test、数据版本、线上候选池 |
| 成本失控 | 预算、模型路由、cost per success Gate |
| 厂商协议碎片化 | Connector 认证、契约测试、兼容矩阵 |
| 日志泄密 | 统一脱敏、最小留存、访问控制和扫描 |
| 过早微服务化 | 模块化单体，按压力拆分 |

## 9. 暂不建设

- 自主多 Agent 群体协作；
- 无人审批的设备写操作；
- 为“企业级外观”拆出的几十个微服务；
- 数据规模尚小时的专用向量数据库集群；
- 同时适配所有 ONVIF 厂商和全部故障；
- 用固定小样本宣传生产准确率。

## 10. 面试表达

**30 秒版本：**

“当前项目已经把可信诊断内核、评测和一台授权设备的只读协议链做实。企业化下一步不是再加故障类型，而是选一个
高价值场景做影子试点，接入 SSO、租户、真实资产、PostgreSQL、模型网关和可观测，再以 MTTR、人工复核率、质量和
cost per success 决定是否扩大。微服务和自动修复都由真实压力与风险证明需要。”

**深挖主线：** 业务先证明价值；安全补身份和最小权限；可靠性补异步、数据与回退；智能能力受模型网关和评测治理；
最后才按负载与团队边界规模化。
