# 基于简历追问的完整标准答案库

> 使用方法：先在 [`01-基于简历的面试追问树.md`](./01-基于简历的面试追问树.md) 中闭卷回答，
> 再查看本页。标准答案不是逐字背诵稿，而是必须覆盖的“结论—风险—设计—证据—边界”。

## 一、可信性

### 1. 为什么把项目称为“可信 Agent”？

**标准答案：**

我所说的“可信”不是模型永远答对，而是模型的权限、事实来源、状态变化和评测结果可以被约束与审计。
模型只负责选择只读工具、组织调查过程并提出 `possible/probable` 候选；工具必须经过 Registry、权限和预算
校验；工具成功结果才转成 Evidence；CitationPolicy 校验结论引用的归属、类型与强度；最终 `confirmed`
只能由 HumanReview 推进。持久化侧还有深层脱敏、CAS、审计和一致性扫描，评测侧要求指标可从逐案例结果复算。

因此“可信”表示系统不会把模型输出直接等同事实，也不会让错误静默进入最终状态。它不表示生产准确率已经得到
证明，更不表示系统无需人工。

**证据落点：** `ToolRegistry.execute()`、`CitationPolicy.validate()`、`SecurityDiagnosisCase.apply_human_review()`。

### 2. 模型到底能做什么、不能做什么？

**标准答案：**

模型能理解模糊描述、选择下一步只读工具、填写工具参数、根据已返回事实生成候选根因和排障建议。模型不能直接
操作 Repository、修改 Case、创建正式 Evidence、绕过工具 allowlist、执行设备写操作或把状态推进为 confirmed。
Runner 只收集 ToolCall、ToolResult、EvidenceDraft 和 ConclusionDraft；Application Service 才把合规草稿转成领域
对象并持久化。

这种边界让概率模型负责柔性规划，确定性代码负责权限、不变量和责任动作。

### 3. 如果模型输出 `confirmed` 怎么办？

**标准答案：**

第一道防线是类型：候选结论的合法可信度不包含 confirmed。第二道是 CitationPolicy，它拒绝 confirmed-like 输入。
第三道是 Case 状态机，最终状态只能通过 `apply_human_review()` 产生。如果外部模型返回非法字符串，结构化解析或
枚举校验会失败，系统返回受控错误，而不是自动纠正为已确认。

不能仅靠 prompt 写“不要输出 confirmed”，因为 prompt 不是安全边界。

### 4. 规则这么多，为什么还需要 LLM？

**标准答案：**

规则适合表达不可妥协的约束，例如权限、状态转换、证据强度和跨故障域不变量；LLM 适合处理用户描述差异、动态
选择调查顺序、组合工具以及组织解释。固定案例确实可以用规则直接分类，但真实输入不是固定字段表。

如果业务以后完全结构化，我会减少 LLM，而不是为了 Agent 而保留它。当前采用的是“概率规划、确定执行、人工终审”。

### 5. 如何避免模型引用不存在或不相关的证据？

**标准答案：**

模型返回的是 Evidence ID，不是任意自然语言引用。Application 在当前 Case 的 Evidence 集合中解析 ID，
CitationPolicy 再验证：ID 是否存在、是否属于当前 diagnosis、Evidence 的 fault_type 是否匹配、可信度所需的设备
事实类型是否齐全。跨 Case、未知 ID 或只引用知识 SOP 的 probable 都会被拒绝。

系统还保留引用修复，但修复只能从当前 Case 的真实 Evidence 中按缺失类型补齐，补齐后必须再次验证；设备事实不足
则降级为 possible，不能为了保留 probable 而伪造引用。

### 6. Evidence 从哪里产生？工具失败算 Evidence 吗？

**标准答案：**

Evidence 来自成功的只读工具结果。Tool 把网关返回的领域快照转成 EvidenceDraft，Application 再赋予诊断归属、
Evidence ID、时间与内容哈希并加入 Case。工具失败只产生结构化 ToolExecutionResult，例如 authentication、timeout、
rate_limited 或 invalid_response，并明确 `evidence_drafts=[]`。

失败不自动成为 Evidence，因为一次超时可能来自客户端网络、代理或预算，而不是设备离线。执行轨迹可以记录失败，
但不能把“没拿到事实”伪装成“设备事实”。

### 7. 为什么 `knowledge_sop` 不能单独支持 probable？

**标准答案：**

SOP 表示历史经验或标准步骤，它能说明“这种症状通常如何排查”，不能证明“当前设备此刻具有什么状态”。probable
至少需要规定数量和类型的现场设备事实，例如设备状态、告警、配置、录像或回放检查。只有 knowledge_sop 时可以形成
possible 候选和排障建议，但不能形成高可信设备结论。

### 8. 人工确认是不是形式按钮？

**标准答案：**

不是。HumanReview 是有 reviewer、action、comment、review_id 和时间戳的领域对象，只能在允许的 Case 状态应用。
confirm/reject/request_more_info 分别驱动不同状态；review 经过 Repository CAS 保存，陈旧版本会返回 409，不自动
重放；保存过程还生成审计事件。也就是说它同时承担状态转换、责任主体、并发保护和审计追踪，而不是 UI 装饰。

## 二、工程职责与架构

### 9. 你最核心的三项工作是什么？

**标准答案：**

第一，设计可信诊断链，把 LLM、只读工具、Evidence、引用策略和人工确认分开。第二，设计设备接入边界，通过资产、
能力、Adapter Registry、授权预算和错误分类接入 Simulator 与 ONVIF 真机。第三，建立评测发布闭环，通过版本化数据集、
分项 Grader、失败归因、历史比较和 Release Gate 判断版本是否退化。

持久化和 RAG 是支撑这三项能力的工程底座：前者保证状态可靠，后者保证经验可治理地复用。

### 10. 为什么选 Ports & Adapters？是不是过度设计？

**标准答案：**

这个项目有三类波动很大的外部依赖：LLM、设备协议和数据库。Port 定义应用真正需要的能力，例如 `LLMClient`、
`DeviceGateway`、`DiagnosisRepository`；Adapter 分别提供 Fake、Static、ONVIF、内存和 SQLite 实现。Domain 不 import
HTTP、SQLAlchemy 或设备 SDK。

它的实际收益是固定评测可以用 Fake/Static 保持确定性，真机验证只替换 Device Adapter，持久化切换不改状态机。
如果项目只有一个脚本和单一依赖，这种分层可能过度；但本项目需要模拟、真机、内存、SQLite 和独立 BGE 多种运行模式，
边界产生了实际测试和替换价值。

### 11. Port 和 Adapter 在项目里举例说明。

**标准答案：**

`DeviceGateway` 是 Port，它只描述查询状态、配置、录像和流信息等业务能力；`StaticDeviceGateway`、
`RoutedDeviceGateway` 和 ONVIF 实现是 Adapter。`DiagnosisRepository` 是 Port；内存仓储与
`SqlAlchemyDiagnosisRepository` 是 Adapter。`EmbeddingPort` 是 Port；FakeEmbedding 和 HTTP BGE 是 Adapter。

判断标准不是文件夹名字，而是 Application 是否只依赖抽象语义、外部技术是否被隔离在实现侧。

### 12. 最有价值的设计漏洞是什么？

**标准答案：**

我认为最有价值的是“构造期脱敏不等于持久化安全”。早期模型 validator 会在对象构造时脱敏，但 Pydantic 对象构造后
的嵌套字典仍可能被直接修改，导致明文凭证绕过 validator 落库。修复方式不是再写一套 Adapter 正则，而是在持久化边界
对 `model_dump(mode="python")` 的独立副本重新 `model_validate`，让同一套领域脱敏规则递归执行，并基于脱敏后的
Evidence 内容重算 hash。测试直接读取 SQLite 原始列，证明明文不存在、hash 与落库内容一致、调用方对象未被修改。

这个问题让我认识到，安全不变量必须针对“最后写入边界”和绕过路径验证，不能只看正常构造流程。

## 三、设备接入

### 13. 没有大量真机，怎么证明设备链路不是 Demo？

**标准答案：**

我把证据分层，而不是用一种测试冒充全部真实性。Static/Fake 验证业务规则；ONVIF simulator 验证协议结构；
Toxiproxy 注入延迟、重置和不可达；本机 FastAPI 契约服务模拟平台业务异常；十轮门禁验证重复稳定性。最后在一台授权
Wi-Fi 摄像头上完成 WS-Discovery、HTTP Digest DeviceInformation、Profiles、Stream URI 和 RTSP Digest OPTIONS。

这证明最小只读协议链不是纯模拟，但我明确不声称多品牌兼容、视频内容准确率或生产 SLA。

### 14. Simulator、Toxiproxy、本机契约服务各模拟什么？

**标准答案：**

ONVIF simulator 模拟设备协议和可控响应，例如 Profile 缺失、码流状态差异；Toxiproxy 模拟传输层问题，例如高延迟、
连接重置和端口不可达；FastAPI 契约服务模拟平台业务接口问题，例如部分事实、错误码、限流和 schema 异常。三者分层后，
失败可以归因到协议、网络或平台业务，而不是统一报“设备异常”。

### 15. 真机验证到什么程度？

**标准答案：**

只验证一台授权 IMOU Wi-Fi 摄像头的最小只读闭环：发现设备服务、HTTP Digest 认证、获取设备信息、查询 Profile、获取
Stream URI，并用 RTSP Digest OPTIONS 验证流端点协议可达。整个过程限制网络交换次数、不自动重试、不执行 PTZ、配置
修改、重启等写操作，也不保存 IP、URI、challenge、原始 XML、画面或设备标识。

它没有验证视频解码、黑屏内容识别、长时间稳定性、多设备并发和多厂商兼容。

### 16. 为什么只做只读？怎样保证没有写操作？

**标准答案：**

诊断阶段的最小权限原则是先观察、后决策，设备写操作可能造成业务中断或安全责任。保证方式不是靠约定：Tool 定义为
READ_ONLY，正式 Runtime 使用最小 allowlist；Gateway Port 只暴露查询方法；AuthorizationManifest 限定操作 scope 和
次数预算；ONVIF Adapter 只实现允许的读取 SOAP Action；验收报告记录 `write_operation_performed=false`。

若未来增加修复动作，必须成为独立阶段，增加审批、幂等、回滚和更高权限，不能混入诊断 ToolLoop。

### 17. HTTP Digest 与 RTSP Digest 遇到了什么问题？

**标准答案：**

最初设备信息请求返回 HTTP 400，之后确认需要 Digest；密码调整后 HTTP Digest 成功。RTSP 首次未认证 OPTIONS 返回
认证 challenge，随后实现 Digest challenge-response。真机又暴露了无 `qop` 的旧式 Digest 兼容分支，修复后完成 RTSP
OPTIONS 闭环。这个过程说明标准协议也存在厂商兼容差异，必须保留严格次数预算、解析边界和脱敏诊断，而不能无限重试。

## 四、数据与并发

### 18. 为什么从内存仓储演进到 SQLite？

**标准答案：**

内存仓储适合早期领域状态机和 Application 测试，反馈快且无基础设施干扰；但它无法验证进程重启恢复、Schema 演进、
事务失败、真实 CAS、审计持久化和备份恢复。SQLite 作为单机基线，用较低运维成本把这些问题变成真实可测试行为。

两种实现遵守同一 Repository Port 和异常契约，所以评测容器仍可用内存，正式单机 Runtime 使用 SQLite。

### 19. CAS 乐观锁怎么实现？为什么冲突后不重试？

**标准答案：**

聚合有 version：新对象为 0，首次保存为 1。更新执行 `UPDATE ... WHERE id=:id AND version=:expected`，同时把 version
设为 expected+1。rowcount 为 1 表示成功；为 0 时先回滚，再查 ID：不存在是 NotFound，存在是 ConcurrentUpdateError。

不自动重试，因为 Agent 运行可能再次调用设备并产生新成本、新事实；HumanReview 是带责任的人工动作，重放可能在已变化
聚合上重复确认。系统返回 409，让调用方刷新后重新决策。CAS 是冲突检测，不是自动合并或完全并发安全。

### 20. 脱敏为什么不能保存前简单 replace？

**标准答案：**

敏感信息可能出现在嵌套 payload、自由文本、Bearer token、URL userinfo、查询参数、卡号、人员 ID 和列表中；简单 replace
容易漏掉结构、误伤普通文本，也无法保证 Evidence hash 对应脱敏内容。项目使用统一 redaction 规则，在 Domain 构造期处理，
持久化边界再对安全副本深层重建，最后根据脱敏内容计算 hash。这样没有两套矛盾规则，也覆盖构造后修改。

### 21. 审计、一致性扫描和备份分别解决什么？

**标准答案：**

审计回答“谁在何时对哪个实体执行了什么动作、结果如何”，采用追加式事件；一致性扫描回答“当前数据库中 Case、Evidence、
Review、Citation 和 Audit 的引用是否自洽”，默认只读，不擅自修复；备份恢复回答“数据库损坏或迁移事故后能否恢复”，需要
同时验证备份创建和恢复结果。三者分别解决行为追踪、静态结构健康和灾难恢复，不能互相替代。

## 五、RAG

### 22. RAG 在系统里贡献了什么？

**标准答案：**

RAG 提供经过治理的历史诊断经验和 SOP，帮助模型理解相似症状、安排排查顺序、补充排除项。它不替代现场设备工具，也不
直接决定 confirmed。confirmed Case 经人工确认后生成 KnowledgeCandidate，再经过 KnowledgeReview 才能成为可召回知识；
检索结果以 knowledge_sop Evidence 进入诊断，并受到 CitationPolicy 的较低证据等级约束。

### 23. 为什么只有 confirmed 知识可检索？

**标准答案：**

如果 candidate 能被召回，模型的一次误判可能写入知识，再影响下一次诊断，形成自我强化污染。rejected 已被否定，retired
可能因固件或流程变化而过期，也不应召回。Repository 的 `search_confirmed()` 和 Retriever 两层过滤，确保只有人工治理后的
confirmed 知识进入结果，同时保留其他状态用于审计。

### 24. Keyword、BGE、Hybrid 怎么选？

**标准答案：**

Keyword 对告警码、设备字段和精确术语可解释、稳定、无需外部服务；BGE 适合用户自然语言和同义表达，但依赖 embedding
质量与服务可用性；Hybrid 将词法与向量候选融合，适合作为候选默认，但权重必须由版本化数据集评测。项目分别保存三组
Recall@K/MRR 基线，BGE 不可用时可以显式降级到 Keyword，同时报告真实 retriever，不能仍标为 Hybrid。

### 25. 怎样避免历史误判污染后续诊断？

**标准答案：**

入口要求来源 Case 已 confirmed；生成后仍是 candidate；人工治理后才 confirmed；检索只读 confirmed；知识保留来源诊断、
结论和 Evidence ID；需要时可 retired；内容进入领域时脱敏；知识 Evidence 不能单独支持 probable。治理、追溯、生命周期和
证据分级共同防止污染，而不是单靠向量库过滤。

## 六、评测与发布

### 26. 怎么知道 Agent 改完是进步还是退步？

**标准答案：**

用固定且版本化的数据集建立 baseline，保持模型、prompt、工具集合和 grader 版本可追踪，再运行 candidate。逐案例保存标签、
工具调用、Evidence、工作流、延迟、模型调用和可得 token，Grader 计算指标，Failure Attribution 定位失败层，History 保存运行，
Release Gate 比较 candidate 与 baseline。判断依据是每个成功任务的质量和成本证据，不是“感觉回答更自然”。

### 27. 为什么不能只看准确率？

**标准答案：**

标签答对可能是偶然命中，也可能通过调用大量无关工具取得。必须同时看 tool precision/recall、Evidence compliance/recall、
workflow success、延迟、调用次数、token 和人工复核率。这样才能区分是模型分类问题、工具规划问题、设备事实缺失、引用违规
还是基础设施故障，并决定修改 prompt、工具、规则还是数据。

### 28. 语义等价标签不在枚举中怎么办？

**标准答案：**

线上结构化输出仍按枚举拒绝未知值，不能自动改标准答案迎合模型。评测中把这类案例标记为 dispute，交人工复核语义是否等价；
若决定接受，需要形成带 reviewer 和理由的数据集新版本，再重新计算基线。这样既保持机器契约严格，又允许标准在审计下演进。

### 29. 不同证据来源如何隔离？

**标准答案：**

每次运行携带 report_kind、source/provenance、模型和数据集版本。Fake/Static 证明确定性逻辑；Simulator/Toxiproxy 证明故障映射；
real_model 证明特定模型在固定案例上的输出；authorized_device 证明授权设备的指定协议链。汇总和门禁按来源分组，不把 Simulator
称作真机、不把 2 条 Validation 称作生产准确率，也不把不可得 token 填成 0。

### 30. 哪些指标能进 Release Gate，如何防伪？

**标准答案：**

适合进入门禁的是能从逐案例记录确定性复算、定义稳定且与发布风险直接相关的指标，例如失败案例数、macro-F1、引用合规、
工具 recall、敏感泄漏数和关键回归。EvaluationOutput 从实际 Case、Evidence、Review 和工具轨迹生成，不接受执行者自报“已确认”或
“合规”；发布包绑定 dataset/grader 版本并校验 manifest。不可得指标保持 null，不能参与伪精确比较。

## 七、最后一分钟收口答案

如果面试官问“这个项目最能体现你什么能力”，可回答：

> 它最能体现我把不确定 AI 能力工程化的能力。我没有把重点放在模型调用本身，而是把模型的权限、设备事实、证据引用、
> 人工责任、并发状态和发布评测都变成确定性边界；同时用 Simulator、真实模型和授权设备分别验证不同层级的假设。我也能
> 清楚说明哪些已经验证、哪些没有验证，而不是用一个 Demo 结果覆盖所有结论。
