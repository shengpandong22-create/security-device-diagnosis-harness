# 压力面试与质疑

## “这不就是 AI 生成的玩具项目吗？”

**建议回答：** “代码开发确实使用了 AI 辅助，但架构约束、审计反例和验收边界是我持续决策的结果。我不以文件量证明
能力，而是可以现场讲清一个漏洞如何被发现和修复。比如构造期脱敏曾会被对象构造后修改绕过，后来我把持久化边界
改为深层重建安全副本，并让 Evidence hash 基于最终脱敏内容重算。您可以继续追问这条实现和测试。”

不要回答：“都是我手写的。”重点是证明你拥有设计和验证，而不是否认工具。

## “为什么写了这么多 Phase，是否过度设计？”

**建议回答：** “Phase 是学习和风险收敛记录，不是运行时架构。面试表达只聚焦六条核心链。早期确实出现过文档与功能
膨胀，所以后期做了多轮逆向审计，关闭了未接入模块、不可复算指标和跨域漏洞。这也是我学到的：交付物数量不等于
产品价值，必须以正式链路和证据闭环为准。”

## “没有生产用户，凭什么说可信？”

**建议回答：** “我说的是工程机制可验证，不说生产效果已验证。只读、人工确认、引用、CAS、审计和门禁都有反例测试；
Simulator 与一台授权设备提供不同强度的证据。用户价值、线上误报率和多厂商兼容仍未验证，我会明确标注。”

## “规则都能判断，为什么还要 Agent？”

**建议回答：** “固定数据集上的标签可以规则化，但真实入口存在模糊描述、动态工具选择和排障步骤组织。LLM 负责柔性部分，
规则负责不可妥协的不变量。如果业务最终完全结构化，我也会减少 LLM，而不是为了 Agent 而 Agent。”

## “只读工具有什么难的？”

**建议回答：** “只读不是工具名字叫 query 就结束。需要 Registry 风险级别、最小 allowlist、资产能力、授权 scope、持久调用
预算、网络交换预算、Adapter 方法集合和审计共同约束。Digest challenge-response 也会影响预算计量。”

## “SQLite 能叫可靠持久化吗？”

**建议回答：** “对单机 Harness，它让我真实验证 migration、事务、CAS、审计和备份恢复；我没有把它包装成分布式高可用。
若进入多实例，需要 PostgreSQL、隔离级别、连接池和运维恢复的重新验收。”

## “你最大的失败是什么？”

**建议回答：** “曾经把完成多个 Phase 当成进展，但正式 Runtime 实际能力更窄；也尝试过 Codex+CodeBuddy 双 Agent 协作，
发现小任务协调成本高于收益。后来沉淀路由原则：小任务直接做，明确机械的中型任务才委派，审查只看规格、关键 diff
和证据。这让我从功能堆叠转向正式链路和 cost per success。”

## “如果现在重做，你会砍掉什么？”

**建议回答：** “先只做摄像头黑屏一个领域，把设备、证据、人工确认、持久化和评测闭环做深；其他故障域在闭环稳定后按
模板扩展。文档也从 Phase 日志改为六条能力链，降低认知成本。”
