# 双 Agent 适用边界与 Codex / CodeBuddy 实验复盘

> 日期：2026-09-15  
> 结论性质：架构决策记录与失败复盘，不是双 Agent 宣传材料

## 1. 为什么最初要打通

最初目标包含两个相互独立的价值：

1. 用户不必守在电脑前，在 Codex 与 CodeBuddy 之间复制需求、结果和返修意见；
2. 在质量不下降的前提下，让 CodeBuddy 承担实现，使完成一个成功任务所消耗的 Codex
   token 少于 Codex 独立实现。

第一个目标是“自动接力”，第二个目标是“经济性”。前期工作证明了进程、worktree、Git、
状态文件和审核能够接力，却太晚才验证经济性。这是本次路线偏离的根因。

## 2. 一手资料给出的边界

### 2.1 复杂度必须由收益证明

Anthropic 在《Building Effective AI Agents》中建议从最简单的方案开始，只在复杂方案能
被评测证明改善结果时才增加复杂度。工作流适合可预定义路径，Agent 适合步骤无法预知的
开放问题；Agent 通常以延迟和成本换取表现。

来源：<https://www.anthropic.com/engineering/building-effective-agents>

### 2.2 多 Agent 主要扩展能力，不天然节省 token

Anthropic 的多 Agent Research 经验显示，多 Agent 通过更多独立上下文和并行探索扩大
计算量；其数据中多 Agent 相对普通聊天使用约 15 倍 token。文章还明确指出，多数编码
任务的真正可并行部分少于研究任务，需要共享上下文、依赖关系密集的领域并不适合当前的
多 Agent 协调。

来源：<https://www.anthropic.com/engineering/multi-agent-research-system>

### 2.3 生成者—评审者循环有前提

Evaluator-optimizer 适合“评价标准清晰，并且迭代反馈能带来可测改进”的任务。它并不表示
所有实现都应天然配一个模型评审者。如果评审者必须重做问题、反馈不可判定或返修收益不
稳定，循环只会增加成本。

来源：<https://www.anthropic.com/engineering/building-effective-agents>

### 2.4 上下文交接必须是高信号压缩

上下文工程的原则是用尽可能少的高信号 token 提高成功概率。子 Agent 的详细探索应留在
自己的上下文，只向协调者返回浓缩结果和可定位的制品；不应把完整过程日志再次灌给主
Agent。

来源：<https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>

### 2.5 Agent 间协议要简单、类型化、可审计

Microsoft 的多 Agent 架构建议强调最小权限、简单性、可审计性和治理，并建议步骤之间使用
必要上下文和类型化载荷。单独 Agent 会引入上下文切换时延和额外维护复杂度。

来源：

- <https://learn.microsoft.com/en-us/agents/architecture/multi-agent-patterns>
- <https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/multi-agent-patterns>

## 3. 哪些场景真正适合双 Agent

### 3.1 独立并行探索

多个方向可以互不依赖地完成，最后只合并结论。例如：

- 一个 Agent 审安全，一个审并发，一个审数据库迁移；
- 多个 Agent 分别检索不同资料源；
- 多个独立模块有清晰所有权，修改文件不重叠。

这里的收益来自并行和上下文隔离，而不是把同一份上下文读两遍。

### 3.2 专业能力或权限真正不同

- 一个 Agent 只有生产只读数据权限，另一个只有代码修改权限；
- 一个模型擅长大规模机械实现，另一个模型专门做安全审计；
- 执行者可以使用工具，裁决者只消费结构化证据。

区别必须落实为能力、权限或信息边界，不能只是提示词里写了不同职位。

### 3.3 实现大、验收小且确定

例如批量生成同构 Adapter、补大量参数化测试、机械迁移 API。执行者修改很多代码，但
协调者可以通过小型 diff 摘要、静态检查和确定性测试低成本验收。

### 3.4 需要独立观点提高置信度

安全审计、风险投票和模型评测中，不同 Agent 独立判断能减少单一路径盲点。此类场景追求
的是质量或置信度提升，通常不是 token 节省，必须确认任务价值能够支付额外成本。

## 4. 哪些场景不适合

- 小改动：交接成本大于实现成本；
- 架构决策：上下文高度耦合，评审者必须理解完整系统；
- 疑难跨模块 Bug：探索路径和局部状态难以压缩交接；
- 需求仍在变化：执行者与评审者会基于不同版本理解任务；
- 没有确定性验收：评审模型只能重新实现或凭感觉判断；
- 修改面和审核面近似相等：不存在“实现大、审核小”的杠杆；
- 为维护双 Agent 协议而开发的元任务：容易形成编排器自我膨胀。

## 5. 为什么本项目当前模式不经济

我们采用的是串行链路：

```text
Codex 写详细规格 -> CodeBuddy 读仓库并实现 -> Codex 再读规格、diff 和上下文审核
```

它不是并行多 Agent，而是 evaluator-optimizer 工作流。当前存在六个结构性问题：

1. **按职位拆分，而不是按独立信息拆分。** 设计师、开发者、审核员名称不同，但三者需要
   理解同一份代码与约束。
2. **审核并不比实现小很多。** 安全路径、PowerShell 兼容和正式接线无法仅凭测试退出码
   判断，Codex 仍需阅读核心 diff 和调用点。
3. **规格成本过高。** 为防止 CodeBuddy 的历史薄弱点，提示词逐渐接近完整实现设计；Codex
   已经做了大量本可直接用于编码的推理。
4. **协议成为新的产品。** 状态机、HANDOFF、attestation、续跑、hash 和探针开始消耗超过
   原业务任务的注意力。
5. **失败跨 Agent 放大。** 执行者遗漏正式接线后，审核者发现问题，再产生返修与复审；单
   Agent 原本可以在同一上下文立即修正。
6. **经济性验证太晚。** 我们先证明“能打通”，后验证“是否值得打通”，顺序反了。

## 6. 本次真实数据

首次冻结条件的 A/B 实验从同一 commit 创建独立 worktree：

| 路径 | Codex input | cached input | output | 结果 |
| --- | ---: | ---: | ---: | --- |
| Codex 独立实现 | 741,517 | 694,784 | 12,469 | 真实入口存在 P1，失败 |
| CodeBuddy 实现 + Codex 审核 | 195,002 | 154,880 | 4,318 | 审核发现两个 P1，失败 |

按 `input + output`，审核调用比独立实现少 73.564%；排除 cached input 后再加 output，差距
只有 24.935%。更重要的是两组都没有通过质量门禁，所以只能称为 `cost per attempt`，不能
称为 `cost per success`。

## 7. 哪些投入仍有价值

这次不是“什么都没得到”。可以保留的通用资产包括：

- worktree 隔离，避免两个执行者破坏同一目录；
- 操作系统进程终态通知，避免模型轮询；
- base/head commit 与结构化状态，支持失败后恢复；
- 精确 token usage 采集，不再用耗尽时间猜消耗；
- Max Turns、最多返修次数和禁止自动 push 等确定性边界；
- 宿主执行批准的测试，模型声明不能替代真实退出码。

应冻结的是“继续扩建通用协议”，不是删除这些已经证明有用的基础设施。

## 8. 今后的三种工作模式

### S：Single Agent，默认模式

Codex 直接设计、实现、测试和修复。用于小任务、架构、安全、疑难问题和高耦合改动。

### D：Delegated Implementation，条件模式

CodeBuddy 实现，宿主运行确定性验收，Codex 只审关键 diff。仅用于稳定、机械、实现量明显
大于审核量的中型任务。

### P：Parallel Specialists，质量模式

多个 Agent 分别处理互不依赖的研究或审计维度，主 Agent 汇总结论。目标是覆盖率、速度或
置信度，不承诺节省总 token。

## 9. 委派准入卡

开始前逐项回答，不能在执行后补答案：

| 问题 | 准入要求 |
| --- | --- |
| 需求是否稳定且可冻结？ | 是 |
| 80% 以上验收能否由确定性命令完成？ | 是 |
| 实现工作量是否预计至少为审核工作量的 3 倍？ | 是 |
| Codex 是否无需重读整个仓库？ | 是 |
| 交付包是否可控制在需求、commit、关键 diff 和测试证据内？ | 是 |
| CodeBuddy 失败后能否从 commit 接管，而非重做？ | 是 |
| 是否不涉及架构方向、真实凭证或破坏性操作？ | 是 |

任意两项为“否”，使用 S 模式。架构方向、真实授权或破坏性操作任意一项命中，直接禁止
无人值守委派。

## 10. 经济性与止损规则

只有两组都成功时才计算：

```text
CodexSavingRate = 1 - CollabCodexTokens / SoloCodexTokens
```

- 节省至少 30%，质量不下降：该任务类别允许 D 模式；
- 节省 10%～30%：只允许高度机械任务；
- 节省不足 10%：使用 S 模式；
- 不降反升：该任务类别禁止委派；
- 一次实现未通过确定性门禁：停止，不调用 Codex 审核；
- 审核发现 P0/P1：最多一次返修，仅当返修后仍可能满足 30% 门槛；
- 连续两个真实任务未形成成功样本：冻结编排器，不再用元任务证明自身。

cached input、uncached input、output、reasoning、总耗时、首次成功率和缺陷数必须分别保存；
不得只使用“多久耗尽额度”作为成本指标。

## 11. 本次错误决策复盘

1. 没有在第一版方案前建立任务路由与经济性门槛；
2. 将技术可行性误当成业务价值；
3. 每次失败后优化局部协议，没有及时重新判断整个方案；
4. 把可恢复、可追踪不断扩展成复杂编排产品；
5. 前四次实验设计缺口本可通过一次完整 pre-mortem 更早发现；
6. 对用户强调“避免消耗”，却没有优先交付用户真正要求的完整结果；
7. 没有及时说明：多 Agent 常用更多总 token，目标只能是减少受限的 Codex token，而非
   假设系统天然更便宜。

## 12. 最终架构决策

Codex / CodeBuddy 链路保留为**可选执行通道**，不再是默认研发流程。项目后续默认 S 模式；
只有通过委派准入卡的真实任务才能进入 D 模式。P 模式只用于天然独立的研究和专项审计。

新的真实任务自然出现以前，不继续制造编排器元任务，不追加协议功能，也不为了得到正向
数据重复实验。这个决定可以被新的成功数据推翻，但不能被主观期待推翻。
