# Phase 2A 首轮固定对照实验报告

## 结论

本轮标记为 `invalid_failed_run`，不能作为改造前后 `cost per success` 基线，也不能据此宣称事件驱动方案已经节省某个比例的额度。

CodeBuddy 的 A、B 两个实现都通过了 6/6 测试，但均未创建任务要求的提交。实验脚本没有在 Codex 审查前验证这一完成门禁，并错误地对不存在的 `HEAD~1` 执行审查。原始输出与 usage JSONL 均保留。

此外，首轮 fixture 的 6 项测试漏掉了“首字符必须为 `a-z`”的三个反例；两个实现都错误接受以点、下划线或连字符开头的别名。测试通过不等于需求通过，这也是本轮无效的独立原因。

## 已修复的实验门禁

- 测试命令改为 fixture 根目录下的 `python -m unittest -v`。
- fixture 新增点、下划线、连字符开头的三个反例，并忽略测试生成的 `__pycache__`。
- CodeBuddy 完成必须同时满足：退出码 0、测试通过、创建新 commit、工作区干净。
- 只有完成门禁通过才允许进入 Codex 审查。
- 基线一致性改为比较两个初始 commit 的 tree hash，不再使用命令输出的真假值。
- 真实复跑不会自动发生；需再次取得用户确认。

## 下一次复跑的单变量约束

保持模型、fixture、prompt、max turns、超时和验收命令不变。只修复实验编排器的门禁与取数错误。若 CodeBuddy 再次未提交，实验应在实现阶段终止并保留现场，不调用 Codex 审核。

## 第二次运行记录

第二次运行同样没有形成有效对照。CodeBuddy A 已正确修改目标文件并通过 9/9 测试，但 PowerShell 7 将 `unittest -v` 写往 stderr 的正常进度转换为 `NativeCommandError`；全局 `ErrorActionPreference=Stop` 导致门禁提前终止。Codex 审核与 B 变体均未执行。

本次仅产生两次 A 轮询调用，实测分别为 31,001 与 62,429 input tokens，合计 93,430；cached input 分别为 26,112 与 52,224。它们属于第二次失败运行成本，不计入成功基线。

进一步的流程修正是把职责放回确定性脚本：CodeBuddy 负责改代码并跑测试；脚本验证“测试通过且只改预期文件”后创建 handoff commit；Codex 只审已经形成的 commit diff。这样不会把 Git 提交这一机械步骤继续交给模型碰运气，也不会放宽代码验收。

## 第三次运行记录

第三次运行首次完整走完 A/B，但仍判为无效：A、B 两个实现都把首字符规则写成 `[a-z0-9]`，错误接受数字开头。fixture 只覆盖了点、下划线和连字符开头，仍漏掉数字开头反例。A 审核识别出这个业务错误；B 审核没有识别出来。两次审核还都因为 Codex 隔离运行环境没有继承宿主 Python PATH 而无法重跑测试，最终均为 `REJECTED`。

本轮实测 A 三次调用共 157,988 input tokens，其中两次轮询为 93,606；B 一次审核为 80,156 input tokens。由于两个实现均违反完整规格且审核未通过，这些仍是失败运行成本，不是 `cost per success`。

由此新增两项确定性修正：fixture 加入 `1camera` 反例；脚本启动时解析宿主 Python 的绝对路径，并把同一路径明确传给 A/B 两个独立审核会话。它避免审核沙箱因 PATH 差异产生假阴性，但不会替审核放宽任何业务判断。
