# 2026-09-15 封版前逆向审计第一轮报告

## 1. 审计目标与纪律

本轮不是继续增加 Phase，也不是证明已有实现全部正确，而是从正式运行、业务真实性、
Harness 不变量、评测可信度和企业落地五个方向反查 Phase 0～11。

本轮只取证和记录，不修改业务代码。严重度定义：

- P0：可能造成越权、敏感泄漏、不可恢复数据破坏或错误自动确认，必须立即阻断；
- P1：不修复就不能支撑当前能力声明、真机封版或企业试用；
- P2：不阻断本地演示，但限制可维护性、可运营性或证明强度；
- Boundary：项目明确未实现的边界，不冒充缺陷，也不得包装为已完成。

## 2. 当前结论

第一轮确认 **0 个 P0、10 个 P1、5 个 P2**。当前工程不是普通“日志/设备信息丢给
大模型”的 Demo：Harness、数据可靠性、评测治理和 Simulator 故障注入都具有明显工程
深度。但是它仍不是企业可部署产品，正式运行链路比 Phase 能力总表窄得多，诊断规则对
矛盾事实的治理、模型语义约束、真实 RAG、API 治理和评测数据规模仍然不足。

一句话判断：

> 工程底座与约束设计较强，正式产品链路和真实业务证明偏浅；适合真机试接入与面试展示，
> 不适合表述为已经生产上线或已经证明规模化诊断准确率。

## 4. P1 发现

### P1-01：正式 Runtime 只覆盖摄像头静态样例和 FakeLLM

**证据**：`build_runtime_container()` 默认调用 `build_camera_registry()`，实例化
`FakeLLM` 与 `StaticDeviceGateway`；实测 `supported_fault_types` 只有
`camera_black_screen`。录像、门禁、报警的独立评测 Container 没有进入正式 Runtime。

**影响**：README 中 Phase 1～4 都已完成，但用户通过正式 API 只能运行摄像头域。面试时
可以说“四域规则与固定评测已完成”，不能说“正式服务支持四域运行”。

**建议方向**：真机封版前先决定正式服务是否只定位摄像头试接入。如果是，应在能力清单
明确分层；如果不是，需要由统一装配矩阵接入四域，而不是继续增加新 Phase。

### P1-02：Phase 5 RAG 没有进入正式诊断工具

**证据**：正式 Runtime 虽创建 `knowledge_repository` 和 `knowledge_service`，但
`build_camera_registry()` 内的 `KnowledgeSearchTool` 没有注入 Retriever。运行时探针显示
`knowledge_tool_has_retriever=False`。BGE/Hybrid 只在 Phase 5 Demo、评测和独立 Adapter 中。

**影响**：当前 RAG 是“可独立运行的检索子系统”，不是 Agent 正式诊断链路的一部分。
知识候选即使经过人工确认，也不会被正式 `knowledge__search` 召回。

**建议方向**：不急于扩大 RAG。先把 confirmed KnowledgeRepository → HybridRetriever →
KnowledgeSearchTool 的依赖装配打通，并保留 BGE 不可用时的显式降级证据。

### P1-03：正式 Runner 没有真实 LLM Adapter，也缺少完整资源预算

**证据**：`adapters/llm` 只有 `FakeLLM`。OpenAI-compatible Client 位于 evaluation，不能
实现 ToolLoopRunner 的 `LLMClient` 正式协议。`ToolLoopBudget` 只有 `max_rounds` 和
`max_tool_calls`，没有 wall-clock deadline、单轮响应大小、Prompt/Completion token 和成本预算。

**影响**：当前完整 Agent Loop 是确定性 Fake Responder 闭环；真实模型只接受受限事实做
结构化评测，没有跑正式 Tool Loop。接真实模型后，时间和成本边界尚不充分。

**建议方向**：这不是设备到货前必须修复的 P0，但必须降低对“真实 Agent 已跑通”的表述。
若接真实模型，应先做独立 Adapter、预算与低频 Validation，不直接替换正式 Runtime。

### P1-04：矛盾 Evidence 的结果依赖列表顺序

**真实探针**：对同一个诊断构造 `online=False` 与 `online=True` 两条 DEVICE_STATUS：

```text
[False, True] → insufficient_camera_facts
[True, False] → device_offline_or_network_unreachable
```

`extract_camera_facts()` 遍历 Evidence 时直接覆盖同类型字段，没有按 `captured_at`、来源、
可靠性或冲突策略决策，也没有产生“事实冲突”状态。

**影响**：多次采样、设备与平台冲突、重跑后累积 Evidence 时，插入顺序可能改变根因。

**建议方向**：建立事实归并协议：同类型事实按时间窗、来源优先级和可靠性选择；无法消解时
输出 conflict 并限制到 possible/inconclusive，不能静默 last-write-wins。

### P1-05：CitationPolicy 只检查结构，不检查可靠性和语义一致性

**真实探针**：两条 `Reliability.LOW` 的 DEVICE_STATUS/DEVICE_STREAM 可以支撑 probable；
摄像头故障域中写入“磁盘已满导致录像丢失”的 summary/root_cause，同样通过 CitationPolicy。

**影响**：当前 Policy 能证明“引用 ID 属于当前诊断且类型数足够”，不能证明被引用事实可靠，
也不能证明结论文本真的由这些事实支持。

**建议方向**：分别治理结构可信与语义可信。确定性层至少增加低可靠性上限、事实新鲜度、
冲突阻断；语义一致性进入 Grader/HumanReview，不要假称 CitationPolicy 已完全解决。

### P1-06：自动引用修复会掩盖模型没有选择证据

**证据**：大量 FakeLLM 测试和固定 Responder 返回空 `cited_evidence_ids`；应用服务的
`repair_cited_evidence_ids()` 会自动选择前两类设备事实，让 probable 通过 Policy。

**影响**：最终结论“引用合规”只能证明 Harness 修复后的结果合规，不能证明模型完成了正确
引用。自动选取也只按 Evidence 类型，不检查与 root_cause 的语义关系。

**建议方向**：报告同时保存 `model_citations` 与 `effective_citations`，把“模型引用准确率”
和“系统最终合规率”分开。正式模式可将空引用直接降级，修复仅作为显式策略而非隐式成功。

### P1-07：规则候选与模型结论可能互相矛盾，API 又不返回规则候选

**证据**：`DiagnosisConclusion` 使用模型 summary/root_cause；`candidate_label` 在结论落库后
由确定性规则独立推导，两者没有一致性门禁。`RunDiagnosisResult` 包含 candidate、证据链、
degraded 和 failure_kinds，但 `RunDiagnosisData` 没有这些字段，API 路由没有返回它们。

**影响**：模型可以给出一个结论文本，规则给出另一个候选；内部报告可能展示二者，而 API
调用方只看到模型结论，无法判断降级和规则解释。

**建议方向**：定义唯一的“对外候选结论”协议，明确模型解释和规则标签的主从关系；API 必须
返回 candidate_label、matched_rule/evidence_chain、degraded 和 failure_kinds。

### P1-08：业务写入与审计追加不是原子操作

**真实探针**：让 `AuditRepository.append()` 抛错，`create_diagnosis()` 向调用方报错，但
`DiagnosisRepository.count()` 已为 1。

**影响**：调用方认为创建失败并重试时可能得到重复冲突；数据库已有业务状态，却没有对应
审计事件。这违背“所有变更都有审计”的强表述。

**建议方向**：短期明确审计为 best-effort 还是强一致。强一致需 Unit of Work/同事务写入；
若不能同事务，应使用 outbox/待补偿状态，而不是在业务 commit 后直接抛出模糊失败。

### P1-09：人工确认 API 没有身份认证与授权

**证据**：`POST /api/v1/diagnoses/{id}/review` 直接信任请求中的 `reviewer` 字符串；API 没有
认证、角色和权限依赖。当前 `run_api.py` 默认绑定 `127.0.0.1`，降低了暴露范围，但不是身份治理。

**影响**：本机任何可访问进程都能伪造 reviewer 并产生 confirmed。若未来改变监听地址，风险
会直接扩大。

**建议方向**：真机本地演示可以保留，但必须把“人工确认”表述为领域边界，不是已完成的企业
身份认证。企业化需要可信身份注入、角色授权、审计 actor 绑定和 CSRF/调用方边界。

### P1-10：ONVIF/可观测/发布 Gate 仍属于专用验证链路

**证据**：ONVIF 与 CrossSourceGateway 由 `eval_device_lab_scenarios.py` 手工装配；正式
RuntimeSettings 没有 ONVIF endpoint、credential reference 或资产加载机制。运行时可观测
只由 `eval_phase9d_simulator_shadow.py` 调用，正式 API 没有 ObservabilityPort。发布 Gate
由脚本运行，仓库无 CI 工作流自动阻塞合并/发布。

**影响**：Phase 9～11 的能力证明很强，但尚未形成一个用户启动正式服务即可使用的产品路径。

**建议方向**：真机到达后不要直接把临时凭证写进 Runtime。先增加一次性受控装配入口，并将
真机报告和 Simulator 报告隔离。CI 与线上指标属于后续企业化工作，不应在封版前临时堆砌。

## 5. P2 发现

### P2-01：评测基础设施明显强于数据规模

正式数据集 `1.0.0` 实测只有 6 例：Dev 2、Validation 2、Test 2；全部来源为 synthetic，
四个故障域的数量分别为摄像头 2、录像 2、门禁 1、报警 1。

这足以验证 Dataset/Grader/Gate 协议，不足以给出具有统计意义的诊断准确率、宏 F1 或泛化结论。

### P2-02：Test Set 的“密封”是代码约定，不是独立权限边界

`DatasetRegistry.cases(test)` 默认拒绝，但调用方可以传 `allow_test=True`；真实模型脚本允许
`--split test` 后直接读取。它能防止误用，不能防止开发者反复在 Test Set 上调参。

建议将 Test 解封绑定独立发布命令和一次性产物记录，并在面试中把它表述为流程治理。

### P2-03：资产目录只能启动时注入

`InMemoryDeviceAssetCatalog` 只有 `get/list_enabled`，正式 Runtime 默认只有一个静态摄像头。
当前没有资产配置文件治理、持久化管理 API、热更新或禁用操作。这符合本地试接入，但不是
企业设备目录。

### P2-04：健康检查不是深度 readiness

`database_ready` 表示组件初始化且 Container 未关闭，不执行实时 SQL；health 也不检查
Device Adapter、BGE、模型或资产。文档已经诚实说明，但运维侧仍缺 liveness/readiness 分离。

### P2-05：工程发布自动化不足

仓库没有 CI workflow；版本仍为 `0.1.0`，项目 description 仍写 “Phase 0”。1633 项测试和
各类 Gate 主要依赖人工运行。它不影响本地正确性，但降低了“发布门禁真正不可绕过”的证明。

## 6. 本轮没有判为缺陷的边界

- SQLite 只支持单机，不等于数据库设计失败；项目明确拒绝 PostgreSQL 等网络数据库。
- Simulator 不是“假测试”；它对协议、错误分类、生命周期和稳定性有真实价值，只是不能替代真机。
- 没有设备写工具是安全设计，而不是能力缺失。
- 不自动重试 Agent/HumanReview 是为了避免重复副作用，并非可靠性缺陷。
- 暂无前端、消息队列、Redis、Kubernetes，不构成本项目当前阶段的 P1。

## 8. 下一轮审计计划

下一轮仍先不修复，重点验证：

1. 四域规则在矛盾、陈旧、重复和多根因事实下的顺序敏感性；
2. Runner 的超时、响应体、超长 observation 和工具批量调用边界；
3. HTTP/ONVIF 的 SSRF、DNS 变化、响应流式上限、XML/SOAP Fault 分类；
4. SQLite 审计、备份、恢复和并发失败后的真实磁盘状态；
5. Grader/Gate 是否存在汇总字段投机、Test Set 误用和同源自证；
6. README、验收文档与正式可达能力逐条对照。

完成第二轮取证后，再统一决定：真机前必须修复项、真机过程中验证项、可以接受并明确说明的
技术债。不得边发现边扩大功能范围。
