# 2026-09-15 封版前逆向审计第二轮报告

## 1. 审计目标与纪律

第二轮继续采用逆向取证：不以测试数量和 Phase 完成状态作为正确性证明，而是主动构造
矛盾事实、慢模型、超大工具结果、不一致评测产物和真实协议边界。审计期间没有修改业务
代码，没有访问真实设备、真实模型、BGE 或外部网络。

严重度沿用第一轮定义：P0 表示必须立即阻断的越权、敏感泄漏、不可恢复破坏或错误自动
确认；P1 表示不修复就不能支撑真机封版、当前能力声明或可信发布；P2 表示不阻断本地
演示，但会削弱兼容性、运维性或证明强度。

## 2. 第二轮结论

本轮确认 **0 个 P0、8 个 P1、5 个 P2**。其中最关键的新结论是：

1. Evidence 顺序敏感不是摄像头规则的单点缺陷，而是四个故障域共有的事实归并缺失；
2. Runner 的轮次/工具次数预算不能阻止慢模型、超大 observation 和模型异常穿透；
3. ONVIF Adapter 验证了 SOAP 与 RTSP 端口，却没有验证设备返回的实际 RTSP URI；
4. 发布 Gate 可被“逐案例失败、汇总指标未同步”的不一致评测对象绕过；
5. HTTP/ONVIF 的响应大小限制发生在响应完整缓冲之后，不是真正的内存上限。

因此，下一步不应增加 Phase，也不应先扩大四域正式 Runtime。应先修“事实确定性、Runner
资源边界、ONVIF 真协议语义、Gate 自证一致性”四条主线，再进行真机验收。

## 3. P1 发现

### P1-01：四个故障域都采用隐式 last-write-wins

四个规则提取器遍历 `case.evidence` 时，对同类事实直接覆盖，没有统一按采集时间、来源、
可靠性和冲突状态归并。真实内存探针得到：

```text
摄像头 [offline, online]  → insufficient_camera_facts
摄像头 [online, offline]  → device_offline_or_network_unreachable

录像存储 [full, normal]   → insufficient_recording_evidence
录像存储 [normal, full]   → storage_capacity_or_pool_issue

门禁事件 [permission_denied, time_window_denied] → access_time_window_denied
门禁事件 [time_window_denied, permission_denied] → permission_not_granted

报警规则 [sensitive, normal] → insufficient_alarm_evidence
报警规则 [normal, sensitive] → alarm_rule_too_sensitive
```

同一事实集合仅改变插入顺序就改变候选标签。多次采样、重跑积累和设备/平台跨来源接入后，
该问题会比 Simulator 单快照场景更频繁。

**修复边界**：先建立统一 `EvidenceResolver`/事实视图。明确时间窗、来源优先级、可靠性、
重复与冲突规则；无法消解时生成 conflict，并把可信度限制为 possible/inconclusive。四个
规则只消费已解析事实，不各自实现一套选择逻辑。

### P1-02：ToolLoopBudget 没有 wall-clock deadline

当前预算只限制 `max_rounds` 和 `max_tool_calls`。本轮注入一次睡眠 0.6 秒的 LLM，在
`max_rounds=1`、`max_tool_calls=1` 下完整等待 0.6 秒，Runner 没有超时中断机制。

**影响**：接真实模型后，网络挂起和供应商尾延迟不能由 Harness 的预算收敛；数据集里的
`timeout_seconds` 只是事后 Grader 评分，不是运行时保护。

**修复边界**：deadline 必须由 Runner 创建并向 LLM/Tool 请求传播；超时输出受控失败，
不得仅在请求结束后统计耗时。

### P1-03：Runner 没有模型/工具结果大小上限，模型异常原样穿透

真实探针中，工具返回 2,000,000 字符 observation，Registry 与 Runner 全量接受并复制到
下一轮模型消息；没有字符、字节或 token 上限。另一个探针让 `LLMClient.complete()` 抛出
`RuntimeError("provider secret detail")`，异常类型和原始消息直接穿透 Runner。

**影响**：单个工具可放大 Prompt、内存和模型成本；供应商异常可能进入 API/日志，破坏稳定
错误协议并泄漏底层细节。

**修复边界**：分别设置单工具 observation、单轮模型输出、累计上下文和模型调用次数上限；
LLM Adapter/Runner 只向上抛稳定、脱敏的错误类别。截断必须显式记录，不能静默伪装完整事实。

### P1-04：ONVIF 返回的实际 RTSP URI 被校验后丢弃

`_stream_uri()` 只检查 `<Uri>` 的 scheme 是否为 `rtsp`，返回值为 `None`；随后
`_rtsp_available()` 固定向配置的 host/port 发送：

```text
OPTIONS rtsp://device.invalid/profile RTSP/1.0
```

因此测试中即使设备返回的 URI 路径、端口或主机不可用，只要固定探针端口对任意 OPTIONS
返回 `RTSP/1.0`，最终仍会得到 `PullStatus.SUCCESS`。

**影响**：这验证的是“某个 RTSP 端口响应”，不是“ONVIF 为该 Profile 返回的流可拉取”。
真机可能出现端口可达但 Profile URI 错误、鉴权失败或具体流不存在，当前实现会误报成功。

**修复边界**：保留设备返回 URI 的安全结构化结果，验证 host/port 与资产 allowlist 一致，
对该 URI 发送 DESCRIBE/SETUP 级只读探针；禁止把含 userinfo 的 URI落库、日志或报告。

### P1-05：ONVIF Profile 选择与事实深度不足以覆盖常见真机

Profile 选择依赖 token/name 包含 `profile_main/main` 或 `profile_sub/sub`。使用
`Profile_1`、`Profile_2`、中文名称或仅通过编码参数区分主子码流的设备会被判定为
`PROFILE_NOT_FOUND`。同时 `GetProfiles` 只保留 token/name，生成的 `StreamSnapshot` 没有
编码、分辨率、帧率和码率事实。

**影响**：当前 Simulator 的 profile 命名正好迎合启发式规则，十轮稳定不能证明对真实厂商
Profile 命名和媒体配置的兼容性。

**修复边界**：优先解析 VideoEncoderConfiguration；提供确定性 fallback 和显式
`ambiguous_profile`，不能依赖英文命名猜测。真机到货后把原始协议事实转成脱敏 fixture，加入
回归集。

### P1-06：发布 Gate 信任可伪造的 SuiteMetrics

`compare_runs()` 已正确从逐案例重算 P0 数量，但六个核心指标仍直接读取
`baseline.grade.metrics` 和 `candidate.grade.metrics`。本轮基于已提交的 Phase 7 基线构造：

```text
candidate_case_passed = False
new_findings = ('forged_new_failure',)
SuiteMetrics 保持与 baseline 相同
gate_allowed = True
blocking_reasons = ()
```

Gate 报告甚至展示了新增失败，但仍允许发布。

**影响**：反序列化外部 JSON、手工拼装或生成流程缺陷造成 cases/metrics 不一致时，非 P0 回归
可绕过发布门禁。内容 hash 只能证明文件未变，不能证明内部自洽。

**修复边界**：Gate 必须从 `CaseGrade.metrics/findings` 重算 SuiteMetrics，或在模型构造时严格
验证两者完全一致；`passed=False` 或新增 ERROR 是否直接阻塞也需形成明确 Policy。

### P1-07：HTTP/ONVIF 响应上限是在完整缓冲之后检查

两个 Adapter 都使用 `client.get/post()` 获得完整 `Response`，随后检查
`len(response.content) > max_response_bytes`。`Content-Length` 提前检查只能覆盖诚实服务器；
chunked、缺失或伪造 Content-Length 时，超大响应已经进入内存才会被拒绝。

**影响**：allowlist 上的异常设备、Simulator 或被接管服务仍能造成不受配置上限约束的内存
占用。配置名 `max_response_bytes` 容易让维护者误认为它是硬上限。

**修复边界**：使用 streaming API，累计读取到上限即关闭响应；XML/JSON 解析只消费受限
字节。ONVIF 与 Security Platform HTTP Adapter 应复用同一受限读取器。

### P1-08：业务状态与追加审计仍没有统一提交语义

第一轮发现的问题经第二轮复核仍成立：业务 Repository 已完成写入后，AuditRepository
`append()` 失败会让调用方收到失败，但业务行仍存在。本轮将其保留为 P1，而不是因“已有
审计表”降级。

**修复边界**：SQLite 模式使用同一 Unit of Work 提交业务状态和审计事件；内存模式保持等价
语义。若选择最终一致，则必须使用 outbox/待补偿状态并返回准确结果，不能既提交业务又向
调用方宣称整个操作失败。

## 4. P2 发现

### P2-01：所有 SOAP Fault 都被分类为认证失败

`_soap()` 只要发现任意 `<Fault>` 就映射为 `AUTHENTICATION`。ActionNotSupported、InvalidArg、
设备忙和厂商内部 Fault 都会被误分。它仍是受控失败，故不定 P1；但会误导降级指标和排障。

### P2-02：BGE HTTP Adapter 的安全与数值校验弱于设备 HTTP Adapter

`HttpBgeEmbeddingAdapter` 接受任意 base URL，没有 endpoint allowlist、响应体/批量输入上限、
稳定错误映射和 close 生命周期；向量只检查 list 与维度，不拒绝字符串、NaN 或 Infinity。
当前正式 Tool 没有接入它，因此暂定 P2；一旦进入正式 Runtime，应升级为 P1 后先修再接。

### P2-03：SQLite 备份保证完整性，但不保证机密性和可信来源

备份使用 SQLite backup API、schema revision、size 与 SHA-256，并在替换前保留 recovery copy，
这些机制是正确的。但备份、manifest 和 recovery copy 没有加密、签名、保留期或显式文件权限
收紧。能同时修改备份和 manifest 的主体可以重新计算 checksum。

当前是本机运维工具，不将其判为安全 P0。企业化时必须把 SHA-256 表述为意外损坏校验，不能
表述为防篡改；敏感数据库备份需要 OS 权限、加密和生命周期策略。

### P2-04：SQLite 并发运行参数仍是最小默认值

Engine 只设置 `check_same_thread=False`，没有显式 WAL、busy timeout 或连接级 PRAGMA 治理。
CAS 能阻止陈旧覆盖，但不能消除多写者的 `database is locked`；当前会受控映射为 503。
单机低并发可接受，真机长时间运行应采集锁冲突指标后再决定是否调整。

### P2-05：评测数据规模与 Test 密封边界没有变化

数据集仍是 Dev/Validation/Test 各 2 条，六条全部 synthetic；Test 仍可由显式
`allow_test=True` 解封。第二轮没有发现新的数据泄漏，但也没有新增证据支持泛化准确率。

## 5. 与第一轮的合并判断

| 主线 | 当前结论 | 真机前动作 |
|---|---|---|
| 事实归并 | 四域系统性顺序敏感 | **必须修复并补四域反序测试** |
| ONVIF | SOAP 可达，但 RTSP URI 与 Profile 语义偏浅 | **必须修复 URI 探针与 Profile 解析** |
| Runner | Fake 闭环可用，真实资源边界不足 | 真机继续 Fake 可暂缓；接真实模型前必须修 |
| Gate | 协议存在，但非 P0 汇总可伪造 | **可信封版声明前必须修复** |
| Audit | 有事件表，但业务与审计非原子 | 真机本地试验可记录限制；产品声明前必须修 |
| RAG | 独立检索能力，未接正式 Tool | 不阻断真机，停止表述为正式诊断 RAG |
| API/Auth | 本机 API 可用，reviewer 不可信 | 本机试验可接受；外部监听前必须加身份边界 |
| 数据集 | 可验证框架，不证明统计准确率 | 持续收集脱敏真机案例，不伪造规模结论 |

## 6. 建议修复顺序

### 批次 A：真机到货前必须完成

1. 统一四域 Evidence 归并与冲突降级；
2. ONVIF 使用实际 Stream URI 做受控只读探针，并完善 Profile 选择；
3. Gate 重算/校验 SuiteMetrics，新增“案例失败但汇总伪造”的反例测试；
4. HTTP/ONVIF 改为真正的流式响应上限。

### 批次 B：真实模型进入正式 Agent Loop 前完成

1. Runner wall-clock、模型次数、上下文与 observation 预算；
2. LLM 稳定错误分类和脱敏；
3. 区分模型原始引用与 Harness 最终引用；
4. 规则候选与模型文本一致性门禁。

### 批次 C：企业试用前完成

1. 业务与审计统一事务或 outbox；
2. HumanReview 身份认证、授权与 actor 绑定；
3. 正式 RAG 装配、BGE 降级和运行时指标；
4. 备份权限、加密、签名、保留与恢复演练；
5. CI 强制执行测试、评测和发布 Gate。

## 8. 封版判断

当前项目可以继续进行受控真机试接入，但还不能“按现状直接封版”。建议把封版门槛从 Phase
数量改为四个可证伪条件：

- 同一 Evidence 集合任意排列，解析结果不变；
- ONVIF 成功必须对应设备返回的具体 Stream URI 可用；
- 超时与超大结果能在 Runner/Adapter 内主动停止；
- 任意 cases/metrics 不一致的评测产物不能通过 Gate。

这四项通过后，再用真机事实补充兼容性和数据集；其余企业化能力作为明确边界推进，而不是
继续用新增 Phase 掩盖正式链路深度不足。

## 9. 修复跟踪

### P1-01：已修复（2026-09-15）

新增统一 Evidence 解析协议：同类事实先比较可靠性，再比较 `captured_at`，最后用
`evidence_id` 做稳定去重；最高可靠性且最新时间相同、payload 不同的事实被显式标记为
conflict，四域规则统一降级到各自的 insufficient 标签，不再任选列表中的最后一条。

验证证据：

```text
统一解析协议测试             → 4 passed
四域规则定向回归             → 76 passed
全量测试                     → 1641 passed
Phase 1～4 固定评测           → 各 5/5，label_accuracy=1.0
外部模型/设备/BGE 调用        → 无
```

当前规则没有硬编码“设备优先于平台”等来源顺序，因为现有 `EvidenceSource.DEVICE_GATEWAY`
不能表达具体采集方。更细的跨来源优先级应在来源模型具备足够语义后增加，不能靠字符串猜测。
